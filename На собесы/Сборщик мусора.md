## ⚙️ Этапы работы GC

### 1️⃣ **Инициация сборки**

- GC запускается:
    
    - при нехватке памяти;
        
    - при вызове `GC.Collect()`;
        
    - при переходе на более старшее поколение;
        
    - или фоново, если включён **background GC**.
        
- Потоки **остановливаются частично** — зависит от режима (см. ниже).
    

---

### 2️⃣ **Маркировка (Mark phase)**

- GC **находит корни** (`roots`): ссылки из стека, статических полей, CPU-регистров, т.д.
    
- Рекурсивно **помечает все достижимые объекты** (alive).
    
- Остальные считаются мусором.
    
- На этом этапе часть работы может идти **в фоне**, без полной остановки всех потоков (background / concurrent GC).
    

---

### 3️⃣ **Остановка мира (Stop the World)**

- Когда GC переходит к критической фазе (компактирование / обновление ссылок), происходит **Stop-the-World (STW)**.
    
- Все потоки, кроме GC, приостанавливаются, чтобы не изменять кучу во время перемещений объектов.
    

---

### 4️⃣ **Сжатие и обновление (Compact phase)**

- Для SOH (Gen 0–2):
    
    - GC **удаляет неиспользуемые объекты**, **перемещает выжившие**, чтобы устранить фрагментацию.
        
    - Обновляются все ссылки на перемещённые объекты.
        
- Для LOH:
    
    - Обычно **только очистка**, без перемещения.
        
- Для POH:
    
    - Объекты остаются на месте.
        
- Для Frozen — GC вообще не трогает.
    

---

### 5️⃣ **Рестарт потоков и постобработка**

- Потоки возобновляются.
    
- GC может выполнить финализацию объектов с деструкторами (`finalizer`).
    
- Освобождает память, обновляет статистику, переходит в "спящий" режим до следующего триггера.
    

---

## ⚙️ Типы GC

Важно упомянуть (особенно для собеседования):

- **Workstation GC** — оптимизирован для UI-приложений (минимум пауз).
    
- **Server GC** — оптимизирован для многопоточности (много heap-сегментов, один на CPU).
    
- **Background / Concurrent GC** — часть сборки выполняется параллельно с работой приложения, уменьшая длительность Stop-the-World.

## 🧩 Области кучи (Heap Segments)

### 1️⃣ Small Object Heap (SOH)

- Здесь хранятся **маленькие объекты** (до ~85 KB).
    
- Делится на **поколения (generations)**:
    
    - **Gen 0** — только что созданные объекты. Собираются чаще всего.
        
    - **Gen 1** — "промежуточные" объекты, выжившие хотя бы одну сборку.
        
    - **Gen 2** — долгоживущие объекты.
        
- После сборки младших поколений объекты могут "продвигаться" вверх.
    
- 💡 _После удаления мусора SOH дефрагментируется (компактизируется)_, чтобы устранить фрагментацию памяти.
    

---

### 2️⃣ Large Object Heap (LOH)

- Для объектов **размером > 85 000 байт**.
    
- Сюда попадают, например, большие массивы.
    
- **Не дефрагментируется** (по крайней мере, до .NET 4.5), т.к. перемещение крупных блоков слишком дорого по времени.
    
- В современных версиях (.NET Core 3.0+) **дефрагментация LOH может быть включена вручную**:
    
    `GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;`
    
- LOH участвует только в **полных сборках** (full GC), то есть когда собирается Gen 2.
    

---

### 3️⃣ Pinned Object Heap (POH)

- Введён в **.NET 5**.
    
- Хранит **закреплённые (pinned)** объекты — те, чей адрес в памяти нельзя менять (например, для передачи unmanaged кода через `fixed`).
    
- Нужен, чтобы pinned-объекты не мешали компактизации других областей.
    
- GC **не перемещает** объекты из POH, и **не компактизирует** эту область.
    

---

### 4️⃣ Frozen Segment / Frozen Objects

- Введён в **.NET 6+** (и активно используется в .NET 8+).
    
- Используется для **неизменяемых (immutable)**, **долгоживущих** данных.
    
- Такие объекты никогда не собираются и не перемещаются.
    
- Идея: если объект больше никогда не изменится и не освободится, зачем тратить время GC на его трекинг.
    
- Например, используется для **строковых литералов**, **readonly данных**, кэшированных неизменяемых структур.
