## ⚙️ Этапы работы GC

### 1️⃣ **Инициация сборки**

- GC запускается:
    
    - при нехватке памяти;
        
    - при вызове `GC.Collect()`;
        
    - при переходе на более старшее поколение;
        
    - или фоново, если включён **background GC**.
        
- Потоки **остановливаются частично** — зависит от режима (см. ниже).
    

---

### 2️⃣ **Маркировка (Mark phase)**

- GC **находит корни** (`roots`): ссылки из стека, статических полей, CPU-регистров, т.д.
    
- Рекурсивно **помечает все достижимые объекты** (alive).
    
- Остальные считаются мусором.
    
- На этом этапе часть работы может идти **в фоне**, без полной остановки всех потоков (background / concurrent GC).
    

---

### 3️⃣ **Остановка мира (Stop the World)**

- Когда GC переходит к критической фазе (компактирование / обновление ссылок), происходит **Stop-the-World (STW)**.
    
- Все потоки, кроме GC, приостанавливаются, чтобы не изменять кучу во время перемещений объектов.
    

---

### 4️⃣ **Сжатие и обновление (Compact phase)**

- Для SOH (Gen 0–2):
    
    - GC **удаляет неиспользуемые объекты**, **перемещает выжившие**, чтобы устранить фрагментацию.
        
    - Обновляются все ссылки на перемещённые объекты.
        
- Для LOH:
    
    - Обычно **только очистка**, без перемещения.
        
- Для POH:
    
    - Объекты остаются на месте.
        
- Для Frozen — GC вообще не трогает.
    

---

### 5️⃣ **Рестарт потоков и постобработка**

- Потоки возобновляются.
    
- GC может выполнить финализацию объектов с деструкторами (`finalizer`).
    
- Освобождает память, обновляет статистику, переходит в "спящий" режим до следующего триггера.
    

---

## ⚙️ Типы GC

Важно упомянуть (особенно для собеседования):

- **Workstation GC** — оптимизирован для UI-приложений (минимум пауз).
    
- **Server GC** — оптимизирован для многопоточности (много heap-сегментов, один на CPU).
    
- **Background / Concurrent GC** — часть сборки выполняется параллельно с работой приложения, уменьшая длительность Stop-the-World.

---

## 🧩 Области кучи (Heap Segments)

### 1️⃣ Small Object Heap (SOH)

- Здесь хранятся **маленькие объекты** (до ~85 KB).
    
- Делится на **поколения (generations)**:
    
    - **Gen 0** — только что созданные объекты. Собираются чаще всего.
        
    - **Gen 1** — "промежуточные" объекты, выжившие хотя бы одну сборку.
        
    - **Gen 2** — долгоживущие объекты.
        
- После сборки младших поколений объекты могут "продвигаться" вверх.
    
- 💡 _После удаления мусора SOH дефрагментируется (компактизируется)_, чтобы устранить фрагментацию памяти.
    

---

### 2️⃣ Large Object Heap (LOH)

- Для объектов **размером > 85 000 байт**.
    
- Сюда попадают, например, большие массивы.
    
- **Не дефрагментируется** (по крайней мере, до .NET 4.5), т.к. перемещение крупных блоков слишком дорого по времени.
    
- В современных версиях (.NET Core 3.0+) **дефрагментация LOH может быть включена вручную**:
    
    `GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;`
    
- LOH участвует только в **полных сборках** (full GC), то есть когда собирается Gen 2.
    

---

### 3️⃣ Pinned Object Heap (POH)

- Введён в **.NET 5**.
    
- Хранит **закреплённые (pinned)** объекты — те, чей адрес в памяти нельзя менять (например, для передачи unmanaged кода через `fixed`).
    
- Нужен, чтобы pinned-объекты не мешали компактизации других областей.
    
- GC **не перемещает** объекты из POH, и **не компактизирует** эту область.
    

---

### 4️⃣ Frozen Segment / Frozen Objects

- Введён в **.NET 6+** (и активно используется в .NET 8+).
    
- Используется для **неизменяемых (immutable)**, **долгоживущих** данных.
    
- Такие объекты никогда не собираются и не перемещаются.
    
- Идея: если объект больше никогда не изменится и не освободится, зачем тратить время GC на его трекинг.
    
- Например, используется для **строковых литералов**, **readonly данных**, кэшированных неизменяемых структур.


## 🧩 Финализатор (`finalizer` / деструктор)

### 🧠 Что это такое

Финализатор — это **специальный метод, который вызывается GC перед уничтожением объекта**, если он определён.  
Он нужен, чтобы **освободить неуправляемые ресурсы**, если они не были освобождены вручную.

В C# он пишется так:

`class MyClass {     ~MyClass()     {         // cleanup code     } }`

> ⚠️ На уровне IL это метод `Finalize()`, который объект унаследовал от `System.Object`.

---

### ⚙️ Как работает

1. Когда объект становится недостижимым, GC **не удаляет его сразу**, если у него есть финализатор.
    
2. GC **перемещает его в специальную очередь финализации (finalization queue)**.
    
3. Отдельный поток финализатора (**finalizer thread**) вызывает `Finalize()` для этих объектов.
    
4. Только **после вызова финализатора** объект считается окончательно готовым к очистке и попадает в **Freachable queue** (ready for collection).
    
5. При следующей сборке память реально освобождается.
    

---

### ⏱️ Важные особенности

- Финализаторы вызываются **асинхронно**, **в неопределённое время**.
    
- Нет гарантии, **когда** он сработает, или что вообще сработает (например, если процесс завершается).
    
- GC вызывает финализаторы **только один раз** для конкретного объекта.
    
- Если объект “оживает” во время финализации (сохранил ссылку на себя в статике), он **снова станет достижимым**.
    

---

### ⚠️ Недостатки финализаторов

- Замедляют сборку мусора: объект живёт дольше (две сборки вместо одной).
    
- Не контролируется порядок вызова — нельзя полагаться на зависимости.
    
- Могут вызывать **долгие паузы** и **нагрузку на finalizer thread**.
    

---

### 🧰 Когда использовать

Только если твой объект **работает с неуправляемыми ресурсами напрямую**:

- файловые дескрипторы;
    
- сокеты;
    
- хэндлы WinAPI (`IntPtr`, `SafeHandle`);
    
- GDI-объекты и т.п.

## ♻️ IDisposable

### 🧠 Что это такое

`IDisposable` — интерфейс, предоставляющий **определённый контракт для явного освобождения ресурсов**.

`public interface IDisposable {     void Dispose(); }`

Метод `Dispose()` вызывается вручную (или автоматически через `using`) и предназначен для **синхронного освобождения ресурсов**.

---

### ✅ Правильный паттерн Dispose (Full Dispose Pattern)

Когда класс содержит **неуправляемые ресурсы**, или управляемые, которые их держат (например, `FileStream`), реализуется такой шаблон:

`class MyResource : IDisposable {     private bool _disposed = false;     private readonly SafeHandle _handle = new SafeFileHandle(IntPtr.Zero, true);      ~MyResource()     {         Dispose(false);     }      public void Dispose()     {         Dispose(true);         GC.SuppressFinalize(this); // подавляем вызов финализатора     }      protected virtual void Dispose(bool disposing)     {         if (_disposed) return;          if (disposing)         {             // освобождаем управляемые ресурсы             _handle?.Dispose();         }          // освобождаем неуправляемые ресурсы         // (например, вызов CloseHandle(_nativePtr))          _disposed = true;     } }`

🔹 `disposing == true` — вызов из `Dispose()` (вручную, управляемо).  
🔹 `disposing == false` — вызов из финализатора (нельзя трогать управляемые объекты, они могут быть уже собраны).  
🔹 `GC.SuppressFinalize(this)` — говорит GC, что финализатор больше не нужен.

---

### 💡 Правила и best practices

1. **Если у класса есть финализатор → почти всегда должен быть IDisposable**.  
    Иначе пользователь не сможет освободить ресурсы вовремя.
    
2. **Если только управляемые ресурсы → финализатор не нужен.**
    
3. **`Dispose()` можно вызывать много раз**, но реализация должна быть **идемпотентной** (не падать при повторном вызове).
    
4. **В современных .NET лучше использовать `SafeHandle`**  
    Вместо ручной работы с `IntPtr` и финализатором — безопаснее и быстрее.
