# ✅ Having, GroupBy

## 🧩 **GROUP BY — что это и зачем?**

**GROUP BY** — это оператор SQL, который **группирует строки в таблице по значению одного или нескольких столбцов**.  
После группировки мы можем применять **агрегатные функции** (COUNT, SUM, AVG, MAX, MIN) **к каждой группе**.

### Пример:

`SELECT department, COUNT(*) FROM employees GROUP BY department;`

Это объединит всех сотрудников по отделам и посчитает, сколько сотрудников в каждом.

**Главная идея GROUP BY:**  
→ _Сначала_ группируем данные.  
→ _Потом_ применяем агрегаты.

---

## 🧩 **HAVING — что это и зачем?**

**HAVING** — это условие, которое применяется **уже после группировки**, то есть **к результатам агрегирования**.

Оно работает как WHERE, но **WHERE нельзя использовать для условий над агрегатами**, поэтому существует HAVING.

### Пример:

`SELECT department, COUNT(*) FROM employees GROUP BY department HAVING COUNT(*) > 10;`

Этот запрос покажет только те отделы, где больше 10 сотрудников.

**Главная идея HAVING:**  
→ Фильтрует группы (а не строки) по агрегированным значениям.

## ⚠️ Почему нельзя использовать WHERE вместо HAVING?

Потому что:

- **WHERE** фильтрует строки _до_ того, как они объединятся в группы.
    
- **HAVING** фильтрует группы _после_ агрегирования.
    

### Ошибка:

`SELECT department, COUNT(*) FROM employees WHERE COUNT(*) > 10     -- так нельзя! GROUP BY department;`

COUNT(*) ещё не существует на этапе WHERE → нужен HAVING.
# ✅ Join

## 🏆 1. INNER JOIN (внутренний) — наиболее частый и **дефолтный** тип

Если ты пишешь просто:

`SELECT * FROM A JOIN B ON A.Id = B.AId`

MS SQL трактует `JOIN` как **INNER JOIN по умолчанию**.

### Что делает:

Возвращает **только те строки**, у которых есть совпадение в обеих таблицах.

---

## 🏆 2. LEFT JOIN (LEFT OUTER JOIN)

Возвращает:

- **все строки из левой таблицы**
    
- совпавшие строки из правой таблицы
    
- если совпадений нет → в полях правой таблицы будут `NULL`
    

### Пример:

`SELECT * FROM Customers c LEFT JOIN Orders o ON c.Id = o.CustomerId`

Покажет всех клиентов, даже тех, у кого нет заказов.

---

## 🏆 3. RIGHT JOIN (RIGHT OUTER JOIN)

То же, что LEFT, но наоборот:

- возвращает **все строки из правой таблицы**
    
- и совпавшие из левой.
    

### Пример:

`SELECT * FROM Orders o RIGHT JOIN Customers c ON o.CustomerId = c.Id`

То же, что LEFT, только поменялись таблицы.

**На собеседованиях часто уточняют:**  
→ _RIGHT JOIN используется редко, LEFT JOIN — почти всегда._

---

## 🏆 4. FULL OUTER JOIN

Возвращает:

- все строки из обеих таблиц
    
- совпавшие и не совпавшие
    
- нехватающие поля заполняются `NULL`
    

### Пример:

`SELECT * FROM A FULL OUTER JOIN B ON A.Id = B.Id`

---

## 🧩 CROSS JOIN

Создаёт декартово произведение:

`кол-во строк в A` × `кол-во строк в B`

Используется редко, но могут спросить.

---

## 🧩 SELF JOIN

Таблица соединяется сама с собой.  
Обычно применяют к таблицам с иерархией — сотрудники и менеджеры.

`SELECT e.Name, m.Name AS Manager FROM Employees e LEFT JOIN Employees m ON e.ManagerId = m.Id;`

---

## 📌 Ключевой момент: какой JOIN по умолчанию?

**В MS SQL, если написать просто JOIN → это INNER JOIN.**

`FROM A JOIN B ON ...`

равно:

`FROM A INNER JOIN B ON ...`

---

## 🧠 Частые вопросы на собеседовании

### ⭐ 1. Чем INNER JOIN отличается от LEFT JOIN?

- INNER возвращает только совпавшие строки.
    
- LEFT возвращает все строки слева + совпавшие справа.
    

### ⭐ 2. Почему RIGHT JOIN почти не используют?

Потому что логически почти всегда удобнее ориентироваться на "левую" таблицу как на основную.

### ⭐ 3. Что будет, если писать WHERE вместо ON?

Это классика.

`SELECT * FROM A LEFT JOIN B ON A.Id = B.AId WHERE B.AId IS NOT NULL`

→ это превращает LEFT JOIN в INNER JOIN, потому что WHERE фильтрует уже после соединения.
# ✅ ООП, SOLID
## 🎯 **ООП — основные принципы**

ООП основано на четырёх ключевых принципах:

## 1. **Инкапсуляция**

Скрытие внутреннего состояния объекта и предоставление безопасных методов для работы с ним.
## 2. **Наследование**

Возможность создавать новые классы на основе существующих.
## 3. **Полиморфизм**

Способность объектов вести себя по-разному при вызове одного и того же метода.
## 4. **Абстракция**

Выделение ключевых характеристик объекта, скрывая детали реализации.

## 🎯 **SOLID — 5 принципов чистого проектирования**

---

## S — **Single Responsibility Principle (SRP)**

**Принцип единственной ответственности**  
Класс должен быть ответственен **только за одну вещь**.
## O — **Open/Closed Principle (OCP)**

**Открыт для расширения, закрыт для модификации**
## L — **Liskov Substitution Principle (LSP)**

**Принцип подстановки Барбары Лисков**

> Объекты подкласса должны полностью заменять объекты базового класса **без изменения поведения программы**.

### Каноничный пример: Прямоугольник → Квадрат

**Почему нарушает LSP?**  
Квадрат — это математически частный случай прямоугольника,  
но **с точки зрения поведения класса** — нет, потому что у квадрата ширина = высоте.

### Пример:

`class Rectangle {     public virtual int Width { get; set; }     public virtual int Height { get; set; }      public int Area => Width * Height; }  class Square : Rectangle {     public override int Width { set => base.Width = base.Height = value; }     public override int Height { set => base.Width = base.Height = value; } }`

Проблема:

`Rectangle r = new Square(); r.Width = 5; r.Height = 10;  // Ожидаем площадь = 50 // Получаем 100, потому что Square связал ширину и высоту.`

Это **нарушение LSP**, а на собеседованиях так и спрашивают.

## I — **Interface Segregation Principle (ISP)**

**Разделение интерфейсов**

Не нужно заставлять класс реализовывать методы, которые ему не нужны.

## D — **Dependency Inversion Principle (DIP)**

**Принцип инверсии зависимостей**

Модули верхних уровней не должны зависеть от конкретных реализаций —  
только от **абстракций**.
## 📘 Итоговый краткий конспект (как шпаргалка для собеса)

### ООП:

1. **Инкапсуляция** — скрываем данные, даём публичные методы.
    
2. **Наследование** — переиспользование кода, иерархия классов.
    
3. **Полиморфизм** — разные реализации одного интерфейса/метода.
    
4. **Абстракция** — оставляем главное, скрываем детали.
    

---

### SOLID:

### **S — SRP**

Класс делает что-то одно.

### **O — OCP**

Расширяем через наследование/композицию, не меняем существующий код.

### **L — LSP**

Подкласс должен вести себя так же, как базовый.  
Квадрат ≠ прямоугольник (нарушение).

### **I — ISP**

Интерфейсы должны быть узкими, а не "толстыми".

### **D — DIP**

Классы зависят от абстракций, а не реализаций.
# ✅ Паттерны

## 📘Порождающие
#### 🔹Абстрактная фабрика 

Позволяет создавать семейства связанных объектов, не привязываясь к конкретным классам создаваемых объектов.
#### 🔹Строитель 

Позволяет создавать сложные объекты пошагово. Строитель даёт возможность использовать один и тот же код строительства для получения разных представлений объектов.

#### 🔹 Фабричный метод 

Определяет общий интерфейс для создания объектов в суперклассе, позволяя подклассам изменять тип создаваемых объектов.

#### 🔹Прототип 

Позволяет копировать объекты, не вдаваясь в подробности их реализации.

#### 🔹Одиночка 


Гарантирует, что у класса есть только один экземпляр, и предоставляет к нему глобальную точку доступа.
## 📘Структурные

#### 🔹 Адаптер 

Позволяет объектам с несовместимыми интерфейсами работать вместе.
#### 🔹 Мост 

Разделяет один или несколько классов на две отдельные иерархии — абстракцию и реализацию, позволяя изменять их независимо друг от друга.

#### 🔹 Компоновщик 


Позволяет сгруппировать объекты в древовидную структуру, а затем работать с ними так, как будто это единичный объект.

#### 🔹 Декоратор 


Позволяет динамически добавлять объектам новую функциональность, оборачивая их в полезные «обёртки».

#### 🔹Фасад 

Предоставляет простой интерфейс к сложной системе классов, библиотеке или фреймворку.
## 📘Поведенческие
#### 🔹 Наблюдатель 

Создаёт механизм подписки, позволяющий одним объектам следить и реагировать на события, происходящие в других объектах.
#### 🔹 Стратегия 

Определяет семейство схожих алгоритмов и помещает каждый из них в собственный класс, после чего алгоритмы можно взаимозаменять прямо во время исполнения программы.
#### 🔹 Цепочка обязанностей 

Позволяет передавать запросы последовательно по цепочке обработчиков. Каждый последующий обработчик решает, может ли он обработать запрос сам и стоит ли передавать запрос дальше по цепи.

#### 🔹 Итератор 

Даёт возможность последовательно обходить элементы составных объектов, не раскрывая их внутреннего представления.

# ✅ Ковариантность и контрвариантность
В C# вариативность относится к:

- **generic-интерфейсам**
    
- **generic-делегатам**
    

С ключевыми словами:

- `out` — ковариантность
    
- `in` — контрвариантность

## 🟦 1. Ковариантность (_covariance_)

### 📌 Определение:

Ковариантность позволяет использовать **более конкретный тип (наследника)** вместо базового типа.

> Можно подставить `Child` там, где ожидается `Parent`.

В C# ковариантность обозначается ключевым словом **`out`**.

---

### ✔ Пример: ковариантность (`out`)

```cs
interface ICovariant<out T> 
{    
	 T GetItem(); 
}
```
## 🟥 2. Контрвариантность (_contravariance_)

### 📌 Определение:

Контрвариантность разрешает использовать **более общий тип (предка)** там, где ожидается более конкретный тип.

> Можно подставить `Parent` там, где ожидается `Child`.

В C# контрвариантность обозначается словом **`in`**.

---

### ✔ Пример: контрвариантность (`in`)

`interface IContravariant<in T> {     void SetItem(T item); }`

# ✅ Открытые дженерики
## 🎯 Что такое открытые (open) дженерики?

**Открытый (open) generic** — это дженерик-тип, у которого **ещё не определены конкретные типы-параметры**.

Пример:

`typeof(List<>) typeof(Dictionary<,>) typeof(IService<>)`

У этих типов _есть параметры_, но нет конкретного T.  
То есть тип **не завершён**, им нельзя создать объект напрямую.

### Это — open generic:

`var t = typeof(List<>);  // открытый`

### Это — closed generic (закрытый):

`var t = typeof(List<string>); // закрытый, T = string`

## 🎯 Что такое закрытые (closed) дженерики?

Это generic-типы, у которых **все параметры заменены конкретными типами**.

Например:

`List<int> Dictionary<string, User> IService<Order>`

Эти типы полностью определены → их можно инстанцировать (`new`).

---

## 🧩 Почему это важно?

Потому что open generics активно участвуют в:

- **DI контейнере .NET**
    
- reflection
    
- построении фабрик
    
- middleware
    
- validation pipelines
    
- MediatR
    
- EF Core
    
- AutoMapper

## 🎯 Зачем нужны открытые дженерики?

### 1️⃣ Чтобы DI контейнер мог создавать зависимости "на лету"

Например:

`services.AddScoped(typeof(IRepository<>), typeof(Repository<>));`

Теперь:

```cs
IRepository<User>    // создаст Repository<User> 
IRepository<Order>   // создаст Repository<Order> 
IRepository<Product> // создаст Repository<Product>
```

То есть DI автоматически **закрывает** generic типы на основании T.

Это один из самых частых практических кейсов.

## 3️⃣ Чтобы строить конвейеры обработки (pipeline)

Пример — MediatR:

`IRequestHandler<TRequest>`

DI должен уметь собирать:

- `IRequestHandler<CreateUserCommand>`
- 
  `IRequestHandler<GetOrdersQuery>`
    
- `IRequestHandler<UpdateProfileCommand>`

Это как раз open generics.

# ✅ IHostedService, IBackGroundService
## 🟦 **IHostedService**

Это интерфейс **верхнего уровня**, описывающий фоновые задачи.

Он содержит два метода:

`Task StartAsync(CancellationToken token); Task StopAsync(CancellationToken token);`

То есть вы сами должны:

- организовать цикл
    
- обработать ошибки
    
- запустить фоновые задачи вручную
    
- корректно остановить выполнение
    

### Пример:

`public class MyHostedService : IHostedService {     private Timer _timer;      public Task StartAsync(CancellationToken token)     {         _timer = new Timer(_ => DoWork(), null, 0, 1000);         return Task.CompletedTask;     }      public Task StopAsync(CancellationToken token)     {         _timer?.Dispose();         return Task.CompletedTask;     }      private void DoWork()     {         Console.WriteLine("Working...");     } }`

Полная свобода, но больше кода.

---

## 🟥 **BackgroundService**

Это **абстрактный класс**, который уже реализует `IHostedService`  
и предоставляет готовый шаблон для **фонового бесконечного цикла**.

Вместо `StartAsync` и `StopAsync` вам нужно переопределить всего один метод:

`protected abstract Task ExecuteAsync(CancellationToken token);`

### Пример:

`public class MyWorker : BackgroundService {     protected override async Task ExecuteAsync(CancellationToken token)     {         while (!token.IsCancellationRequested)         {             Console.WriteLine("Working...");             await Task.Delay(1000, token);         }     } }`

То есть:

- BackgroundService = уже готовая обвязка
    
- IHostedService = пишешь всё руками
    

---

## 🔥 Основные отличия:**

|Особенность|IHostedService|BackgroundService|
|---|---|---|
|Является шаблоном?|❌ нет|✔ да|
|Нужно писать цикл вручную?|✔ да|❌ нет|
|Нужно писать StopAsync вручную?|✔ да|❌ нет|
|Для простых фоновых задач?|❌ редко|✔ да|
|Использование|гибкие/особые сценарии|стандартные фоновые процессы|

---

## 🧠 Что спрашивают на собеседовании

### ❓ _“Является ли BackgroundService лайфтаймом?”_

→ Нет, это hosted service, а не lifetime.

### ❓ _“Как регистрировать IHostedService?”_

`services.AddHostedService<MyWorker>();`

### ❓ _“Сколько экземпляров создаёт AddHostedService?”_

→ Один. Он регистрируется как Singleton.

(И это логично — один фоновой процесс на приложение.)

---

## 📌 Краткое резюме (как шпаргалка)

- **Transient / Scoped / Singleton** — это DI lifetimes.
    
- **IHostedService** — фоновые задачи, а не lifetime.
    
- **BackgroundService** — удобная абстракция поверх IHostedService.
    
- AddHostedService всегда создаёт **Singleton**.
    
- IHostedService — ручной контроль Start/Stop.
    
- BackgroundService — автоматический цикл через ExecuteAsync.
# ✅ Исключения
если исключение и в catch  и в finally, кто кого затрет и почему (finally)
## 🎯 1. Если исключение возникает и в `catch`, и в `finally`, кто кого перетрёт?

### ✔ Короткий ответ:

**Исключение из finally всегда перезапишет любое предыдущее исключение — и из try, и из catch.**

`finally` — выполняется _последним_, и если внутри него бросить исключение, оно **перекрывает** всё, что было раньше, потому что именно оно выходит наружу.

Причина:

- CLR фиксирует исключение из try
    
- затем фиксирует исключение из catch
    
- но finally выполняется последним, и его исключение **замещает** предыдущее  
    → только оно долетает наружу

### ❗ Важный факт:

Если в finally есть `return`, он **ещё и проглотит исключение**, вообще полностью уничтожив его.
## 🎯 2. Можно ли писать несколько catch с одним типом исключения?

### ✔ Короткий ответ:

**Да, можно**, но **только если у catch есть разные when-условия**.

Пример:

`try { } catch (Exception ex) when (ex.Message.Contains("SQL")) {     // SQL errors } catch (Exception ex) when (ex.Message.Contains("FILE")) {     // Filesystem errors }`

Это легально, потому что блоки отличает фильтр `when`.

---

### ❌ А вот так — нельзя:

```cs
catch (Exception)
catch (Exception)
```

Ошибка компиляции:  
**"A previous catch clause already catches all exceptions of this or of a super type"**

---

### 🎯 Как работает фильтрация `when`?

Важно: if-условие тут не помогает — именно `when` даёт особое поведение.

Механизм:

1. Исключение кидается.
    
2. CLR проверяет все блоки `catch` **сверху вниз**.
    
3. Если тип совпадает, проверяется фильтр `when`.
    
4. Первый `catch`, у которого `when == true`, срабатывает.
    

### Фильтр when НЕ меняет стек вызовов (в отличие от rethrow через throw ex).

Это важный плюс.
## ❓ 3. Что поймает `catch (Exception)`?

**Не всё**.

Он НЕ поймает:

### ❌ StackOverflowException

(процесс падает полностью)

### ❌ OutOfMemoryException

может не пойматься, зависит от контекста

### ❌ ThreadAbortException

полупойманный (поток всё равно будет абортирован)

### ❌ AccessViolationException (в некоторых случаях)

### ❌ OperationCanceledException

…поймает, но обычно это контрпродуктивно.

---

## ❓ 4. Что поймает `catch` без типа?

`catch { }`

Равноценно:

`catch (Exception)`

---

## ❓ 5. Разница между throw и throw ex?

### ✔ Правильно бросать вот так:

`throw;`

→ сохраняется оригинальный stack trace (то, что нужно).

### ❌ А вот так — почти всегда ошибка:

`throw ex;`

→ Стек **обнуляется** и меняется точка возникновения ошибки.

На собеседовании это важный вопрос.

---

## ❓ 6. Можно ли бросать исключение из финализатора?

Можно, но:

- исключение **игнорируется**
    
- .NET просто его глотает
    
- и пишет в лог Debug: "Unhandled exception inside finalizer"
    

---

## ❓ 7. Можно ли бросать исключение из статического конструктора?

### ✔ Да, можно

### ❌ Но класс становится **неприменимым**, любая попытка обращения → TypeInitializationException

# ✅ Pattern Matching
## 🎯 Что такое Pattern Matching?

**Pattern Matching** — это механизм, позволяющий проверять:

- типы,
    
- формы данных,
    
- значения,
    
- структуры,
    

и **одновременно извлекать данные** (deconstruction), без явных кастов, if’ов и switch’ей.

То есть это “умный switch + умный if”.
## 🎯 Что чаще всего спрашивают на собеседовании?

### 1) Отличие pattern matching от `is`/`as`

- `is`/`as` → просто проверка типа/каст
    
- pattern matching → проверка + извлечение + фильтры + комплексные условия
    

---

### 2) Что делает `var` pattern?

Принимает значение независимо от типа.

---

### 3) Что делает discard `_`?

Игнорирует значение.

---

### 4) Отличие switch expression от switch statement

- expression должен возвращать значение
    
- выражение обязательно должно быть исчерпывающим
    
- нельзя fall-through
    
- нельзя default, вместо него — `_`
# ✅ Модификаторы доступа
## 🔥 Полная таблица модификаторов доступа C#

|Модификатор|Доступен внутри класса|В текущей сборке|В других сборках|Наследникам|
|---|---|---|---|---|
|**private**|✔|❌|❌|❌|
|**private protected**|✔|✔ (но только в том же классе/типе и наследниках из сборки)|❌|✔ (но только если наследник в той же сборке)|
|**protected**|✔|❌ (если не наследник)|❌ (если не наследник)|✔ (в другой сборке тоже)|
|**internal**|✔|✔|❌|❌|
|**protected internal**|✔|✔|✔ (но только наследникам)|✔|
|**public**|✔|✔|✔|✔|
## 🎯 1. **private**

- Доступ только внутри **того же класса или структуры**.
    
- **Не доступен наследникам**.
## 🎯 2. **protected**

- Доступ внутри класса **и всех наследников**, даже если они в других сборках.
## 🎯 3. **internal**

- Доступно **только внутри одной сборки**.
    
- Не важно — наследование или нет.
## 🎯 4. **protected internal** — ОЧЕНЬ ЛЮБИМЫЙ КАВЕРЗНЫЙ ВОПРОС

Многие ошибаются и думают, что это ограниченный доступ внутри сборки.  
Но **это фактически объединение protected И internal**.

То есть:

✔ внутри сборки доступно всем  
✔ в другой сборке доступно наследникам  
❌ в другой сборке НЕ доступно не-наследникам

Правильный смысл:

> “доступно либо наследникам, либо всем в той же сборке”
## 🎯 5. **private protected** — это уже реже спрашивают, но часто путают

(появился только начиная с C# 7.2)

Это **пересечение** private И protected.

То есть:

✔ доступно наследникам  
❌ но только если они находятся в той же сборке

Внешняя сборка → наследник НЕ получит доступа.
## 🎯 6. **public**

Доступен везде.

 ## 🧠 Краткий конспект (как шпаргалка)
### **private** — только внутри класса

### **protected** — внутри класса + наследники (любая сборка)

### **internal** — только внутри сборки

### **protected internal** — внутри сборки + наследники в других сборках

### **private protected** — только наследники внутри сборки

### **public** — доступно всем

# ✅Middleware
## 🚦 Что такое Middleware?

Middleware — это **компоненты конвейера обработки HTTP-запроса**, где каждый может:

✔ выполнить логику  
✔ решить — передавать ли запрос дальше  
✔ изменить запрос/ответ

Работают **цепочкой (pipeline pattern)**.
## 🧱 Основные методы построения pipeline

### 🔹 `Use(...)`

- Позволяет **выполнить логику и передать дальше** (`next()`).
    
- Может **решить не передавать дальше**, прервав цепочку.
    

`app.Use(async (context, next) => {     Console.WriteLine("Before");     await next(); // передаём дальше     Console.WriteLine("After"); });`

💡 Это _единственный_ из трёх методов, где можно выполнять код **до и после** следующего middleware.

---

### 🔹 `Run(...)`

- **Окончание цепочки** — _не передаёт запрос дальше_.
    
- Обычно используется для финальной обработки (например, отдача статичного ответа).
    

`app.Run(async context => {     await context.Response.WriteAsync("End of pipeline"); });`

💡 Если вызвать `Run`, все последующие middlewares _не выполняются_.

---

### 🔹 `Map(...)`

- Создаёт **ветвление по пути** запроса.
    
- Работает как `if (path.StartsWith(...))`.
    

`app.Map("/api", branch => {     branch.Run(async context =>     {         await context.Response.WriteAsync("API section");     }); });`

💡 Ветка работает **независимо от основного pipeline**.
## # ❓Каверзный вопрос: "В каком порядке выполняются middleware?"

👉 **В том, в котором объявлены в коде.** Порядок критически важен.

Например:

`app.UseAuthentication(); // должно быть выше app.UseAuthorization();  // иначе пользователь не будет аутентифицирован`

---

## 🛠 Как сделать свой Middleware (двумя способами)

### 1️⃣ **Функциональный через `Use`**

`app.Use(async (context, next) => {     var sw = Stopwatch.StartNew();     await next();     Console.WriteLine($"Request took {sw.ElapsedMilliseconds}ms"); });`

### 2️⃣ **Классический через класс + extension**

`public class LoggingMiddleware {     private readonly RequestDelegate _next;      public LoggingMiddleware(RequestDelegate next) => _next = next;      public async Task InvokeAsync(HttpContext context)     {         Console.WriteLine("Before");         await _next(context);         Console.WriteLine("After");     } }  public static class LoggingMiddlewareExtensions {     public static IApplicationBuilder UseLogging(this IApplicationBuilder app)         => app.UseMiddleware<LoggingMiddleware>(); }`

Использование:

`app.UseLogging();`

---

## 🔍 Каверзные вопросы (ТОП)

---

### ❓1. Что будет, если не вызвать `next()` в `Use`?

👉 Все последующие middleware **не выполнятся**.

---

### ❓2. Можно ли в `Run` вызвать `next()`?

👉 ❌ Нет. `Run` — _терминальный middleware_.

---

### ❓3. Как обработать исключения во всём конвейере?

👉 Через **Exception Handling Middleware**, важно разместить _в начале_:

`app.UseExceptionHandler("/error");`

Или свой:

`app.Use(async (context, next) => {     try     {         await next();     }     catch (Exception ex)     {         // обработка     } });`

---

### ❓4. Что произойдёт, если middleware сделает `response.WriteAsync(...)`, а потом вызовет `next()`?

👉 Если последующий middleware тоже пишет в response — получим **два ответа → ошибка**, _если заголовки уже отправлены_.

---

### ❓5. Можно ли инжектить сервисы с DI в middleware?

👉 Да, при использовании конструктора. `UseMiddleware<MyMiddleware>` создаёт экземпляр через DI.

---

### ❓6. Что такое `Middleware short-circuiting`?

👉 Прерывание цепочки (например, проверка авторизации).

---

### ❓7. Чем `Map` отличается от `MapWhen`?

- `Map` → по **пути**
    
- `MapWhen` → по **произвольному условию**
    

`app.MapWhen(ctx => ctx.Request.Query.ContainsKey("debug"), branch => {     branch.Run(async ctx => await ctx.Response.WriteAsync("Debug mode")); });`

---

## 📌 Краткий конспект

|Метод|Передаёт дальше|Может прервать|Ветвление|Типичный сценарий|
|---|---|---|---|---|
|`Use`|✔|✔|❌|Авторизация, логирование|
|`Run`|❌|✔|❌|Финальная обработка|
|`Map`|✔|(внутри ветки)|✔|API, static files|
|`MapWhen`|✔|(внутри ветки)|✔|Сложные условия|

---

## 🎯 Итог для собеса

- Middleware = конвейер
    
- `Use` — можно до/после
    
- `Run` — конец цепочки
    
- `Map` — ветвление
    
- Порядок расположения критичен
    
- Исключения ловим только сверху
    
- Можно писать свои через класс + extension
    
- Если забыли `next()` → short-circuit
# ✅ Фильтры
## 🧠 Что такое фильтры?

**Фильтры (Filters)** — это механизм ASP.NET Core MVC, который позволяет выполнить **дополнительную логику до и после выполнения частей обработки запроса**:

📌 До/после

- вызова действия (Action)
    
- выполнения модели
    
- обработки исключений
    
- формирования результата (Result)
    

Обычно используются для:  
✔ логирования  
✔ авторизации  
✔ кэширования  
✔ обработки ошибок  
✔ валидации запросов

---

## 🧩 Типы фильтров

| Тип               | Интерфейс                                           | Когда выполняется                            |
| ----------------- | --------------------------------------------------- | -------------------------------------------- |
| **Authorization** | `IAuthorizationFilter`, `IAsyncAuthorizationFilter` | До всего (первый)                            |
| **Resource**      | `IResourceFilter`, `IAsyncResourceFilter`           | До/после всего, кроме Auth                   |
| **Action**        | `IActionFilter`, `IAsyncActionFilter`               | До/после выполнения метода контроллера       |
| **Exception**     | `IExceptionFilter`, `IAsyncExceptionFilter`         | При возникновении исключений                 |
| **Result**        | `IResultFilter`, `IAsyncResultFilter`               | До/после формирования результата (View/JSON) |

---

## 📌 Порядок вызовов фильтров (очень важно!)

### 🔁 Вход в фильтры

`Authorization → Resource → Action → Result`

### 🔁 Выход из фильтров

`Result → Action → Resource → Authorization`

То есть **stack-based порядок (как матрёшка)**:

 `- Authorization     - Resource        - Action           - Result        - Resource  - Authorization`

📌 _Exception-фильтр не участвует в цепочке — он вызывается только при ошибке!_

---

## 🔥 Каверзные вопросы (реально спрашивают)

---

### ❓1. Что будет, если фильтр Authorization отклонит запрос?

👉 Остальные фильтры **не будут выполнены**, включая Action и Result.

---

### ❓2. Что будет, если в ActionFilter не вызвать `next()`?

`public async Task OnActionExecutionAsync(ActionExecutingContext context, ActionExecutionDelegate next) {     // ...     // await next(); ← Если не вызвать → действие не выполнится }`

👉 **Middleware-style logic** → цепочка прерывается → контроллер не вызывается.

---

### ❓3. Какой фильтр перехватывает исключения?

✔ `IExceptionFilter`

Но если Exception произошёл **внутри Authorization**, он может не быть перехвачен — зависит от того, на какой стадии ошибка.

---

### ❓4. В каком порядке вызываются фильтры с одинаковым типом?

👉 По `Order` свойству.

`[CustomFilter(Order = 1)] [AnotherFilter(Order = 2)]`

🚨 _Меньший Order выполняется первым._

---

### ❓5. Можно ли использовать DI в фильтрах?

✔ Да, но **в классовых** фильтрах, не в атрибутах.

Если фильтр — атрибут:

`public class MyFilter : Attribute, IActionFilter {     // ⚠ DI здесь НЕ сработает }`

То лучше так:

`services.AddControllers(options => {     options.Filters.Add<MyFilter>(); // DI ок });`

---

### ❓6. В чём разница между IResultFilter и IActionFilter?

|ActionFilter|ResultFilter|
|---|---|
|работает вокруг метода контроллера|работает вокруг формирования ответа|
|не видит результат|видит и может менять|

---

# 🛠 Простой пример ActionFilter

`public class LoggingActionFilter : IActionFilter {     public void OnActionExecuting(ActionExecutingContext context)     {         Console.WriteLine("Before action");     }      public void OnActionExecuted(ActionExecutedContext context)     {         Console.WriteLine("After action");     } }`

Регистрация:

`services.AddControllers(options => {     options.Filters.Add<LoggingActionFilter>(); });`

---

# 🎯 Конспект (запомнить!)

|Тип фильтра|Интерфейс|Стадия|Может прервать?|
|---|---|---|---|
|Authorization|IAuthorizationFilter|самый первый|✔|
|Resource|IResourceFilter|до всего (кроме Auth)|✔|
|Action|IActionFilter|до/после метода|✔|
|Exception|IExceptionFilter|при ошибке|❌ только при ошибке|
|Result|IResultFilter|до/после результата|✔|

🧠 _Порядок выполнения → Authorization → Resource → Action → Result_

✔ "Что будет если в ActionFilter не вызвать `next()`?"  
✔ "Где лучше логировать?" (Action или Resource)  
✔ "В какой момент можно модифицировать результат?" (ResultFilter)  
✔ "Как правильно обработать исключения?" (ExceptionFilter)  
✔ "Разница между AuthorizationFilter и Middleware?"  
👉 AuthorizationFilter работает уже **в MVC уровне**, а Middleware — **на уровне HTTP-pipeline**.

# ✅ Атрибуты
## 📌 Что такое атрибуты?

**Атрибуты (Attributes)** — это _метаданные_, которые можно присваивать классам, методам, свойствам, параметрам и т.д.  
Они **не меняют поведение напрямую**, но **могут быть использованы через Reflection**, чтобы изменить логику программы.

> Это как «ярлыки», на основе которых может приниматься решение во время выполнения.

---

## 🔍 Как выглядят атрибуты

`[Obsolete("Use NewMethod instead")] public void OldMethod() { }`

Другие примеры:

- `[HttpGet]`, `[Authorize]`, `[Required]`, `[Range]`, `[Serializable]`
    
- `[DllImport]`, `[ThreadStatic]`, `[Route]`
    

---

## 🧠 Что происходит "под капотом"?

- Атрибуты — классы, наследующие от `System.Attribute`
    
- Не влияют на код напрямую
    
- В runtime могут быть прочитаны через **Reflection**
    

---

## 🛠 Создание кастомного атрибута

`[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method, AllowMultiple = false, Inherited = true)] public class MyCustomAttribute : Attribute {     public string Description { get; }      public MyCustomAttribute(string description)     {         Description = description;     } }`

Использование:

`[MyCustom("Это мой кастомный атрибут")] public class TestClass { }`

---

## 📥 Как получить атрибут (Reflection)

`var attribute = typeof(TestClass)     .GetCustomAttributes(typeof(MyCustomAttribute), inherit: true)     .FirstOrDefault() as MyCustomAttribute;  Console.WriteLine(attribute?.Description);`

---

## 📌 AttributeUsage — ключевые параметры

`[AttributeUsage(     AttributeTargets.Method | AttributeTargets.Class, // где можно применить     AllowMultiple = false,  // можно ли использовать несколько     Inherited = true)]      // наследуется ли`

|Параметр|Описание|
|---|---|
|AttributeTargets|К чему может быть применён|
|AllowMultiple|Разрешает повторное использование|
|Inherited|Наследуется ли в дочерние типы|

---

## 🔥 Каверзные вопросы на собеседовании

---

### ❓1. Можно ли применять атрибут несколько раз?

👉 Да, если `AllowMultiple = true`.

`[MyCustom("test1")] [MyCustom("test2")] // Ок`

---

### ❓2. Можно ли атрибут применять к переменным?

👉 Нет. Атрибуты используются к _членам типа_, но **локальные переменные не поддерживаются**.

---

### ❓3. Что будет, если у атрибута нет суффикса _Attribute_?

✔ Можно писать без суффикса, но класс **обязан** его содержать.

`[MyCustom] // Ok public class MyCustomAttribute : Attribute { }`

---

### ❓4. Когда атрибут влияет на поведение напрямую?

📍 Только если механизм, который использует Reflection, **читает его и действует** (например, MVC, EF Core, логгер и т.п.)

---

### ❓5. Можно ли атрибуту передавать параметры?

✔ Да — через **конструктор и свойства**.

`[MyCustom("important", Level = 5)]`

---

### ❓6. Можно ли читать значение атрибута во время компиляции?

🚨 В основном атрибуты читаются **во время выполнения (Runtime)**  
🧪 _Исключение — compile-time анализаторы и source generators (косвенно)_

---

## 📚 Конспект

|Что|Описание|
|---|---|
|Атрибут|Класс, наследующий `System.Attribute`|
|Назначение|Метаданные, которые читаются через Reflection|
|Пути применения|Методы, классы, свойства, параметры, сборки|
|Свойства|`Target`, `AllowMultiple`, `Inherited`|
|Исполнение|Runtime через Reflection|
|Часто используется|MVC, DI, EF, сериализация, валидация|
# ✅ Асинхронность
## 🚀 Асинхронность в .NET — краткий обзор

Асинхронность реализуется через:

- `async/await`
    
- `Task` / `ValueTask`
    
- компилятор автоматически генерирует **state machine**
    

---

## 🔁 State Machine (машина состояний)

Когда метод помечен как `async`, компилятор преобразует его в **автомат**, который:

- запоминает точку выполнения
    
- продолжает выполнение после `await`
    
- возвращает `Task` (или `ValueTask`)
    
- автоматически сохраняет переменные (closure)
    

### Пример

`public async Task DoAsync() {     await Task.Delay(100);     Console.WriteLine("Done"); }`

Компилятор генерирует примерно:

`state = 0 await Task.Delay state = 1 восстановление контекста`

---

## 📦 Task

- Представляет **объект асинхронной операции**
    
- Всегда **heap allocation** (создаётся в куче)
    
- Можно **дождаться** (`await`) или **подождать синхронно** (`.Result`)
    
- Поддерживает **ContinueWith, статус, отмену**
    
- Если результат уже доступен — всё равно создаётся Task
    

`public async Task<int> GetAsync() => 42;`

---

## ⚡ ValueTask

- Структура (`struct`) → **без аллокации в куче**
    
- Используется, **когда результат часто доступен сразу**
    
- Если уже вычислен → ValueTask не создаёт Task
    
- Если результат надо ждать → внутренне содержит Task
    

`public async ValueTask<int> GetFastAsync() => 42;`

---

📌 **ValueTask нельзя awaited дважды без сохранения результата!**

`var a = GetFastAsync(); await a;   // OK await a;   // ❌ может привести к ошибке`

**Task — можно awaited сколько угодно раз.**

---

## 🧠 Когда использовать ValueTask?

|Сценарий|Task|ValueTask|
|---|---|---|
|Большинство асинхронных методов|✔||
|Часто результат доступен синхронно||✔|
|Высоконагруженные сценарии (микрооптимизация)||✔|
|SSE, кеши||✔|
|EF Core internal||✔|
|Внешний API|✔|😐 _(не рекомендуется)_|

---

## 💣 Каверзные вопросы

---

### ❓1. Можно ли возвращать `void` в async методах?

👉 Только в **event handler**  
Иначе → лучше `Task`. Нельзя awaited.

---

### ❓2. Что если бросить исключение в async void методе?

👉 Исключение **не поймается через try/catch**. Улетит в **SynchronizationContext**.

---

### ❓3. Почему async метод не может иметь `ref/out` параметры?

👉 Потому что **state machine меняет метод в набор состояний** — `ref/out` невозможно сохранить.

---

### ❓4. Можно ли сделать async-конструктор?

👉 Нет. Делают через **factory method**:

`public static async Task<MyClass> CreateAsync() {     var obj = new MyClass();     await obj.InitAsync();     return obj; }`

---

### ❓5. Что лучше – `Task.CompletedTask` или `new Task()`?

✔ `Task.CompletedTask` — уже выполненный Task **без аллокации**

---

### ❓6. Нужно ли добавлять configureAwait(false)?

👉 **В ASP.NET Core обычно не нужно** — SynchronizationContext отсутствует.

|Task|асинхронная операция на куче|

# ✅ IAsyncEnumeralbe
## 🚀 Что такое IAsyncEnumerable?

`IAsyncEnumerable<T>` — это **асинхронный поток данных**, который позволяет:

- получать элементы **поштучно**
    
- **асинхронно** (через `await`)
    
- **лениво** (yield постепенно отдаёт результаты)
    
- **не блокировать поток**
    

Аналог **IEnumerable**, но с асинхронностью.
## 🔥 Главное отличие от IEnumerable

| IEnumerable                   | IAsyncEnumerable                  |
| ----------------------------- | --------------------------------- |
| MoveNext() → bool             | MoveNextAsync() → ValueTask<bool> |
| синхронный                    | **асинхронный**                   |
| `foreach`                     | `await foreach`                   |
| IEnumerable не работает с I/O | I/O-friendly                      |

## 📘 Краткий конспект (шпаргалка)

- IAsyncEnumerable — асинхронный ленивый поток данных
    
- использовать через `await foreach`
    
- async-итераторы используют `yield return`
    
- передача CancellationToken — через `[EnumeratorCancellation]`
    
- MoveNextAsync возвращает `ValueTask<bool>`
    
- поддерживается стримингом в ASP.NET
    
- EF Core может возвращать IAsyncEnumerable
    
- не потокобезопасен
    
- нужен пакет System.Linq.Async для LINQ
# ✅ HealthCheck
## 📌 Что это такое?

Health Checks — это механизм проверки **состояния приложения** и его зависимостей (БД, кеш, внешние сервисы). Используется для **инфраструктурного мониторинга и оркестраторов** (Kubernetes, Docker, Load Balancer).
## 🧠 Статусы

|Статус|Описание|
|---|---|
|**Healthy**|Всё ок|
|**Degraded**|Работает, но не идеально|
|**Unhealthy**|Не работает|
# ✅ MapMetrics
## 📌 Что это?

Эндпоинт для экспорта **метрик Prometheus** (через зачастую _YARP / OpenTelemetry / prometheus-net_). Позволяет собирать данные о:

✔ запросах  
✔ времени обработки  
✔ ошибках  
✔ потреблении памяти
## 🆚 HealthCheck vs MapMetrics

|Feature|HealthCheck|MapMetrics|
|---|---|---|
|Отвечает "жив ли сервис"|✔|❌|
|Видность проблем|Да (логически)|Да (статистически)|
|Используется пациентами|Kubernetes|Prometheus|
|Эндпоинт|`/health`|`/metrics`|
|Событие|Текущее состояние|История + статистика|
