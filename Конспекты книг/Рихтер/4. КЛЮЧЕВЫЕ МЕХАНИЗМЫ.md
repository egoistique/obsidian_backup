
# 🧨1 Исключения и управление состоянием

## 🕹 **Продуктивность вместо надёжности»** 👇

---

### 📘 Общая идея

Автор показывает, что в .NET Framework и управляемом коде в целом **предпочтение отдаётся продуктивности разработки, а не надёжности выполнения**.  
Причина — огромное количество потенциальных источников ошибок, которые невозможно (и непрактично) учитывать все.

---

### 🕹 Исторический контекст

- Автор начинал с **BASIC**, затем перешёл на **Assembler**, потом на **C** и **C++**.
    
- Раньше программисты тщательно контролировали выделение памяти, проверяли результаты функций, обрабатывали ошибки вручную.
    
- В .NET этот подход часто игнорируется — разработчики редко обрабатывают исключения вроде **OutOfMemoryException**, хотя это возможно.
    

---

### ⚙️ Почему код стал «неустойчивым»

1. **Объектно-ориентированное программирование** и удобства композиции повышают продуктивность, но скрывают множество неявных операций, которые могут привести к сбоям.  
    Пример:
    
    `Boolean f = "Jeff".Substring(1, 1).ToUpper().EndsWith("E");`
    
    – может вызвать исключения на любом шаге, но программист это не контролирует.
    
2. **Компилятор C#** автоматически выполняет множество действий:
    
    - упаковка значимых типов;
        
    - создание массивов параметров;
        
    - генерация классов замыканий;
        
    - вызов перегруженных операторов, методов расширений, делегатов и т.д.
        
3. **CLR** также неявно:
    
    - вызывает виртуальные методы, загружает сборки, сериализует объекты;
        
    - генерирует массу исключений (OutOfMemoryException, NullReferenceException, InvalidCastException и т.п.);
        
    - выполняет JIT-компиляцию и финализацию объектов.
        
4. **.NET Framework** — огромная библиотека, где любое обращение к типу может породить исключение.  
    → Контролировать все возможные ошибки **практически невозможно**.
    

---

### 🧩 Пример: метод `OneStatement`

Простой однострочный метод на C# порождает десятки неявных операций в IL-коде.  
Каждая из них — потенциальный источник исключения.  
→ Сделать его «устойчивым» невозможно.

---

### 🧠 Почему допускается ненадёжность

- Учесть все ошибки **непрактично и невозможно**.
    
- Ошибки редки, поэтому предпочтена **продуктивность разработки**.
    
- Исключения полезны тем, что **необработанные ошибки завершают приложение**, выявляя проблемы на стадии тестирования.
    

---

### ⚠️ Опасность перехвата всех исключений

- Некоторые компании не хотят аварийного завершения, и ловят `System.Exception`.
    
- Это может привести к **порче состояния программы**.  
    Пример: метод `Transfer` (перевод денег между счетами) может оставить систему в неконсистентном состоянии.
    
- Продолжение работы после порчи состояния — **угроза безопасности**.
    

---

### 🧰 Способы повышения надёжности

1. **Использовать finally для критических изменений состояния**  
    Пример:
    
    `try { /* ничего */ } finally {     from -= amount;     to += amount; }`
    
    — поток нельзя прервать внутри `finally`.
    
2. **Контракты кода (`System.Diagnostics.Contracts`)**  
    Позволяют проверять корректность аргументов до изменения состояния.
    
3. **CER (Constrained Execution Regions)**  
    Предварительная загрузка и компиляция кода блоков `catch` и `finally`, чтобы избежать исключений при их выполнении.
    
4. **Транзакции (`System.Transactions.TransactionScope`)**  
    Обеспечивают целостность состояния — изменения либо все применяются, либо ни одно.
    
5. **Более явная работа с блокировками (`Monitor.Enter`)**  
    Лучше:
    
    `bool lockTaken = false; try {     Monitor.Enter(lockObj, ref lockTaken);     // ... } finally {     if (lockTaken) Monitor.Exit(lockObj); }`
    
6. **FailFast**  
    Если состояние повреждено без возможности восстановления:
    
    `Environment.FailFast("Critical error", exception);`
    
    — аварийно завершает процесс, записывая информацию в журнал Windows.
    

---

### 🚨 Итоги

- Управляемый код .NET — мощный инструмент для **повышения производительности разработки**,  
    но он жертвует **гарантированной надёжностью исполнения**.
    
- После непредвиденных исключений нельзя полагаться на сохранность состояния.
    
- Если приложение **не может позволить себе сбои** (ОС, СУБД), лучше использовать **неуправляемый код**.
    
- Для большинства обычных программ управляемый код подходит идеально —  
    он ускоряет разработку и делает программы проще, пусть и менее надёжными.


## ** 🧩 Приёмы работы с исключениями**  

---

### ⚙️ Общие принципы

- Исключения — мощный инструмент, **но ими нужно пользоваться осознанно**.
    
- Основная ошибка — **перехват всех исключений подряд**, что скрывает сбои и мешает отладке.
    
- Разделение ответственности:
    
    - **Разработчики библиотек** → не должны определять политику обработки ошибок.  
        Их задача — **гарантировать целостность состояния**, корректно выбрасывать исключения и не скрывать их.
        
    - **Разработчики приложений** → определяют, какие исключения обрабатывать и как реагировать.
        

---

### 🧩 Работа с состоянием

- **Избегать повреждения состояния** объектов.
    
- Проверять входные параметры (контракты).
    
- Менять состояние только если это необходимо.
    
- При ошибке — восстанавливать состояние или корректно завершать операцию.
    

---

### 🔹 Используйте блоки `finally`

- `finally` — код, который выполняется **всегда**, даже если произошло исключение.
    
- Применяется для **очистки ресурсов** (файлов, потоков, блокировок).
    
    `try {     FileStream fs = new FileStream(@"C:\data.bin", FileMode.Open);     Console.WriteLine(100 / fs.ReadByte()); } finally {     fs.Close(); // всегда выполнится }`
    
- Конструкции `lock`, `using`, `foreach`, `finalizer` автоматически создают `try/finally`:
    
    - `lock` → снимает блокировку в `finally`;
        
    - `using` → вызывает `Dispose`;
        
    - `foreach` → вызывает `Dispose` у итератора;
        
    - `Finalize` → вызывает `Finalize` базового класса.
        

---

### ❌ Не перехватывайте все исключения (`catch (Exception)`)

- Перехватывая `Exception`, вы утверждаете, что:
    
    - понимаете причину и
        
    - знаете, как безопасно восстановиться — что **почти никогда не так**.
        
- Библиотеки не должны решать, что считать ошибкой — это ответственность приложения.
    
- Если исключение не обработано, CLR завершает процесс → нормально для тестирования.
    
- В продакшене число необработанных исключений должно быть **минимальным**.
    

📌 Если состояние повреждено и восстановить его невозможно —  
вызовите `Environment.FailFast()` → немедленное завершение процесса.

---

### ⚠️ Когда `catch (Exception)` допустим

- Если нужно выполнить действия и **повторно сгенерировать** исключение:
    
    `catch (Exception) {     LogError();     throw; // повторная генерация }`
    
- Никогда не “глотайте” исключение без `throw` — это **сокрытие ошибки** и риск нарушения безопасности.
    
- FxCop (анализатор кода) проверяет, чтобы в `catch (Exception)` был `throw`.
    

---

### 🔄 Корректное восстановление после исключения

- Перехватывайте **только ожидаемые исключения**, с понятной причиной:
    
    `try {     result = CalculateCell(); } catch (DivideByZeroException) {     result = "Ошибка: деление на ноль"; } catch (OverflowException) {     result = "Ошибка: переполнение"; }`
    
- Не перехватывайте `System.Exception`, `OutOfMemoryException`, `StackOverflowException` —  
    их обработка бессмысленна или небезопасна.
    

---

### 🧨 Отмена незавершённых операций

- Если операция прервалась — нужно **откатить частичные изменения**.
    
    `try {     formatter.Serialize(fs, rootObj); } catch {     fs.Position = beforeSerialization;     fs.SetLength(fs.Position);     throw; // повторное исключение }`
    
- Здесь перехватываются **все исключения**, но обязательно с **повторным `throw`**.
    
- Цель — восстановить согласованное состояние, не скрывая сам сбой.
    

---

### 🔒 Сокрытие деталей реализации (абстракция)

- Иногда нужно заменить низкоуровневое исключение на **более осмысленное**:
    
    `catch (FileNotFoundException e) {     throw new NameNotFoundException(name, e); }`
    
- Это сохраняет **контракт метода** — вызывающий код видит логичное исключение.
    
- Но есть недостатки:
    
    - искажается `StackTrace` (место ошибки смещается);
        
    - затрудняется отладка.  
        Поэтому использовать с осторожностью.
        

---

### 📎 Добавление контекста к исключению

- Вместо генерации нового исключения можно **добавить данные** в `Data`:
    
    `catch (IOException e) {     e.Data.Add("Filename", filename);     throw; }`
    
- Так сохраняется исходное исключение и его стек.
    

---

### ⚙️ Примеры из CLR

- CLR иногда **преобразует исключения**:
    
    - Конструктор типа → `TypeInitializationException`;
        
    - Вызов через отражение → `TargetInvocationException`.
        
- Нужно анализировать `InnerException`, чтобы узнать первопричину.
    
- При использовании **динамических типов (dynamic)** этого не происходит — исходное исключение проходит напрямую.
    

---

### 🧭 Итоги

- **Блоки finally** — обязательно для очистки.
    
- **catch** должен быть точечным и осознанным.
    
- **Нельзя “глотать” Exception.**
    
- **Отменяйте операции** при сбоях, восстанавливайте состояние.
    
- **Абстрагируйте детали** реализации, но не теряйте контекст ошибки.
    
- **FailFast** при повреждённом состоянии.
    
- Главная цель — **устойчивость и предсказуемость поведения**, а не замалчивание ошибок.

## ⚠️ Необработанные исключения

### 🔹 Что это такое

- Когда CLR не находит подходящий `catch` для исключения → возникает **необработанное исключение (unhandled exception)**.
    
- При его появлении **CLR уничтожает поток**, где оно произошло.
    
- Это значит: произошла **ошибка, не предусмотренная разработчиком**, и программа находится в **непредсказуемом состоянии**.
    

📌 Необработанные исключения — **признак серьёзной ошибки** в приложении.  
Пользователь должен сообщить о ней разработчикам.

---

### 🔹 Политика обработки

- **Разработчики библиотек**: не должны заниматься необработанными исключениями.
    
- **Разработчики приложений**: должны определять политику их обработки.
    
- **Рекомендация Microsoft** — использовать **политику CLR по умолчанию**:
    
    - при необработанном исключении Windows:
        
        1. создаёт запись в журнале событий (**Event Viewer → Windows Logs → Application**);
            
        2. добавляет событие в **Reliability Monitor** (список программ, закрывшихся из-за исключений).
            

---

### 🔹 Журналы и диагностика

- В журнале можно увидеть:
    
    - имя и версию исполняемого файла,
        
    - тип исключения,
        
    - метаданные проблемного метода и IL-смещение (анализ через **ILDasm**).
        
- Все управляемые ошибки группируются в контейнер **CLR20r3**.
    

---

### 🔹 Windows Error Reporting (WER)

- После сбоя Windows предлагает **отправить отчёт в Microsoft**.
    
- Разработчики могут **зарегистрироваться на WinQual (Windows Quality)**, чтобы получать отчёты об ошибках своих приложений.
    
- Для этого сборки должны быть **подписаны VeriSign ID (Authenticode)**.
    
- Можно реализовать **собственную систему логирования необработанных исключений** (например, для внутренней отладки).
    

---

### 🔹 Как подписаться на необработанные исключения в коде

В разных типах приложений — разные механизмы:

|Тип приложения|Способ обработки|
|---|---|
|**Обычные .NET-приложения**|`AppDomain.UnhandledException`|
|**Windows Store / UWP**|`Windows.UI.Xaml.Application.UnhandledException`|
|**Windows Forms**|`Application.ThreadException`, `NativeWindow.OnThreadException`, `Application.OnThreadException`|
|**WPF**|`Application.DispatcherUnhandledException`, `Dispatcher.UnhandledException`, `Dispatcher.UnhandledExceptionFilter`|
|**Silverlight**|`Application.UnhandledException`|
|**ASP.NET (Web Forms)**|`TemplateControl.Error`, `HttpApplication.Error`|
|**WCF**|`ChannelDispatcher.ErrorHandlers`|

---

### 🔹 Особые случаи — серверные приложения

- Сервер не должен отправлять клиенту подробности об исключениях (это **опасно** и бесполезно).
    
- Сервер должен:
    
    - записать исключение в журнал,
        
    - уведомить клиента о сбое (без технических подробностей),
        
    - при необходимости перезапустить себя.
        
- В некоторых случаях (например, SQL Server) перезапуск невозможен → система должна продолжить работу безопасно.
    

---

### 🔹 Исключения повреждённого состояния (CSE — _Corrupted State Exceptions_)

- Это **исключения, вызванные ошибками машинного кода или CLR**, а не управляемой логикой.
    
- CLR **по умолчанию не позволяет** управляемому коду их перехватывать (и даже `finally` не выполняется).
    

**Примеры Win32-исключений CSE:**

`EXCEPTION_ACCESS_VIOLATION EXCEPTION_STACK_OVERFLOW EXCEPTION_ILLEGAL_INSTRUCTION EXCEPTION_IN_PAGE_ERROR EXCEPTION_PRIV_INSTRUCTION STATUS_UNWIND_CONSOLIDATE ...`

**Как перехватывать (по особым правилам):**

- пометить метод атрибутами:  
    `[HandleProcessCorruptedStateExceptions]`  
    `[SecurityCritical]`
    
- либо включить старую политику через `legacyCorruptedStateExceptionPolicy = true` в `.config`.
    

**Соответствие типам .NET:**

- `EXCEPTION_ACCESS_VIOLATION` → `AccessViolationException`
    
- `EXCEPTION_STACK_OVERFLOW` → `StackOverflowException`
    
- остальные → `SEHException`
    

---

### 🔹 Проверка стека перед рекурсией

Метод `RuntimeHelper.EnsureSufficientExecutionStack()`:

- проверяет, хватит ли стека для вызова;
    
- при нехватке выбрасывает `InsufficientExecutionStackException`;
    
- полезен при рекурсивных вызовах.
    

---

### 🧭 Вывод по главе

- Необработанное исключение = **критический сбой**.
    
- CLR завершает поток или процесс → правильно.
    
- Разработчику важно:
    
    - логировать проблему,
        
    - уведомлять пользователей,
        
    - не пытаться “восстанавливаться” после критических ошибок.

## 🪲 Отладка исключений (Debugging Exceptions)

### 🔹 Поддержка в Visual Studio

- В Visual Studio есть окно **Debug → Exceptions**.
    
- Позволяет задать, **когда отладчик должен останавливаться**:
    
    - при **генерации (Thrown)**;
        
    - или только при **необработанном исключении**.
        

---

### 🔹 Как использовать

1. В дереве выбрать категорию **Common Language Runtime Exceptions**.
    
2. Развернуть пространства имён и типы (`System`, `System.IO`, и т.д.).
    
3. Отметить нужные исключения:
    
    - если включить флажок **Thrown**, отладчик остановится **в момент генерации** исключения,  
        — полезно, когда неизвестно, где оно обрабатывается;
        
    - если флажок **снят**, отладчик остановится **только если исключение не обработано**.
        

---

### 🔹 Пользовательские исключения

- Можно добавить свои типы исключений вручную → кнопка **Add**.
    
- Ввести полное имя (`Namespace.MyException`).
    
- Тип не обязан быть наследником `System.Exception` — допускаются не-CLS-совместимые типы.
    
- Если есть одноимённые исключения из разных сборок, Visual Studio их не различает (ограничение).
    

---

### 🔹 Пожелания автора (Рихтера)

- Было бы удобно, если бы Visual Studio умела:
    
    - автоматически импортировать все типы исключений из сборки;
        
    - различать исключения с одинаковыми именами по сборкам.
        

---

### 🧭 Итог 

- Visual Studio позволяет **гибко управлять остановками при исключениях**.
    
- Режим **Thrown** — полезен для поиска места возникновения;  
    режим **Unhandled** — для отладки логики обработки.
    
- Можно добавить и отслеживать собственные типы исключений.

## ⚡ Скорость обработки исключений

### 🔹 1. Общие принципы

- В сообществе часто считают обработку исключений **медленной**, но:
    
    > Исключения — **неотъемлемая часть объектно-ориентированной архитектуры** .NET.  
    > Их нельзя заменить на `true/false` или коды ошибок (`enum`, `HRESULT`).
    
- Альтернатива (коды ошибок):
    
    - Увеличивает **объём кода** и **риск ошибок**.
        
    - Замедляет работу (ручные проверки и фильтрация результатов).
        
    - Ухудшает читаемость и надёжность.
        

💡 **Вывод:** Исключения — оптимальное средство обработки ошибок в управляемом коде.

---

### 🔹 2. Разница между C++ и .NET

|Особенность|Неуправляемый C++|Управляемый .NET|
|---|---|---|
|Учет созданных объектов|Компилятор ведёт внутренний “учёт”, вызывает деструкторы при исключениях|Управляемая куча и GC освобождают память автоматически|
|Объем сгенерированного кода|Большой (много служебного кода)|Меньше кода → выше производительность|
|Обработка исключений|Требует сложной внутренней логики|Проще и быстрее благодаря CLR и GC|

✅ **.NET быстрее и компактнее**, чем C++ при обработке исключений, за счёт управляемой среды.

---

### 🔹 3. Особенности реализации и быстродействия

- Производительность зависит от:
    
    - версии **JIT-компилятора**,
        
    - **архитектуры процессора** (x86, IA64, ARM),
        
    - **версии .NET Framework**.
        
- У разных платформ — **разная скорость** обработки исключений.
    
- Рекомендация:
    
    > Тестируйте производительность исключений **на каждой целевой платформе**.
    

---

### 🔹 4. Мониторинг производительности

- Используйте **Performance Monitor (perfmon.exe)**.
    
- Счётчики: _“.NET CLR Exceptions”_.
    
    - Показывают количество выброшенных, перехваченных и необработанных исключений.
        
    - Помогают выявить “горячие точки” с частыми исключениями.
        

---

### 🔹 5. Когда исключения действительно замедляют работу

- Если метод **часто выбрасывает исключения** (например, при парсинге некорректных данных).
    
    - Пример: `Int32.Parse("abc")` → `FormatException`.
        
    - Частые ошибки пользователей → массовая генерация исключений → падение производительности.
        

💡 **Решение Microsoft:**  
Добавлен метод `TryParse`:

`public static bool TryParse(string s, out int result);`

- Возвращает `true/false` вместо исключения.
    
- Исключения генерируются только при **непредвиденных ошибках** (например, `ArgumentException`, `OutOfMemoryException`).
    

---

### 🔹 6. Практические рекомендации

1. **Не избегайте исключений** из-за страха “потери производительности”.
    
2. **Исключения должны быть редкими** — при сбоях, а не при нормальной работе.
    
3. Если пользователи жалуются на частые ошибки и низкую скорость:
    
    - Добавьте методы `TryXxx` (например, `TryParse`, `TryOpen`).
        
4. Если всё работает стабильно — **оставайтесь при стандартных исключениях**.
    

---

## 🧭 Области ограниченного выполнения (Constrained Execution Regions, CER)

### 🔹 1. Зачем нужны CER

- В обычных приложениях (Word, Excel, калькулятор) **высокая надёжность не обязательна** — сбой просто завершает процесс.
    
- В серверных и критичных системах (например, SQL Server) требуется:
    
    - **устойчивость к сбоям**,
        
    - **гарантированное выполнение кода очистки или восстановления**.
        

CER обеспечивает:

> **Гарантированное выполнение блоков `catch` и `finally` даже при критических ошибках.**

---

### 🔹 2. Потоки и домены приложений

- CLR хранит состояние в объекте `AppDomain`.
    
- Если поток в домене вызывает необработанное исключение:
    
    - Можно выгрузить **только домен**, не завершая весь процесс.
        
- CER полезны, когда нужно **защитить общее состояние** между доменами.
    

---

### 🔹 3. Проблема асинхронных исключений

- Некоторые исключения могут произойти **в любое время** (например, при загрузке сборки, JIT-компиляции, вызове статического конструктора).
    
- Если это случится внутри `finally`, код очистки **может не выполниться**.
    

---

### 🔹 4. Пример (небезопасный код)

`try {     Console.WriteLine("In try"); } finally {     Type1.M(); // вызов статического конструктора, может упасть }`

Если статический конструктор `Type1` выбросит исключение — `finally` не завершится.

---

### 🔹 5. Решение с CER

`RuntimeHelpers.PrepareConstrainedRegions(); try {     Console.WriteLine("In try"); } finally {     Type2.M(); }`

`[ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)] public static void M() { }`

- `PrepareConstrainedRegions()` сообщает JIT-компилятору **подготовить весь код блока** (`try`, `catch`, `finally`) **заранее**.
    
- Загружаются все типы, конструкторы, методы → исключения возможны **до входа в try**, а не внутри.
    

---

### 🔹 6. Атрибут ReliabilityContract

`[ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)]`

**Определяет надёжность метода.**

|Параметр|Назначение|
|---|---|
|`Consistency`|степень влияния метода на состояние|
|`Cer`|гарантия выполнения|

#### Consistency

- `MayCorruptProcess` — может повредить весь процесс
    
- `MayCorruptAppDomain` — может повредить домен
    
- `MayCorruptInstance` — может повредить объект
    
- `WillNotCorruptState` — не повредит состояние
    

#### Cer

- `None` — гарантий нет
    
- `MayFail` — может завершиться неудачно
    
- `Success` — гарантированное успешное завершение
    

💡 Если атрибут не указан:

`[ReliabilityContract(Consistency.MayCorruptProcess, Cer.None)]`

---

### 🔹 7. Рекомендации по надёжным методам

- Делайте методы **маленькими** и **изолированными**.
    
- Не выделяйте память.
    
- Не вызывайте **виртуальные** или **интерфейсные методы**.
    
- Не используйте **делегаты**, **рефлексию** и **упаковку** (boxing).
    
- Можно подготовить методы вручную:
    
    `RuntimeHelpers.PrepareMethod(handle); RuntimeHelpers.PrepareDelegate(delegate);`
    

---

### 🔹 8. Дополнительно

- **StackOverflowException** всегда завершает процесс, кроме случаев размещённой CLR (hosted mode).
    
- Метод `ExecuteCodeWithGuaranteedCleanup` обеспечивает гарантированную очистку:
    
    `RuntimeHelpers.ExecuteCodeWithGuaranteedCleanup(     TryCode tryBlock,     CleanupCode cleanupBlock,     object userData);`
    

---

### 🧩 Итог

|Раздел|Суть|
|---|---|
|**Скорость обработки исключений**|Исключения не “медленные” — они безопаснее и продуктивнее кодов ошибок. Производительность снижается только при их частом возникновении.|
|**Области ограниченного выполнения (CER)**|Позволяют гарантировать выполнение `finally` и защиту состояния даже при сбоях. Используются в критичных системах (.NET runtime, SQL Server).|
## 📘 Контракты кода (Code Contracts)

---

### 📘 Что такое контракты кода

**Контракты кода (Code Contracts)** — механизм _декларативного документирования логики и ограничений_ внутри программы.

Контракты:

- описывают **ожидания и гарантии** поведения кода;
    
- повышают **надёжность**, **понятность** и **тестируемость**;
    
- позволяют **рано находить ошибки** и **документировать API**.
    

---

### 🧩 Виды контрактов

|Вид контракта|Что проверяет|Когда проверяется|Пример|
|---|---|---|---|
|**Предусловие (Precondition)**|Корректность аргументов|В начале метода|`Contract.Requires(x > 0)`|
|**Постусловие (Postcondition)**|Корректность результата и состояния после выполнения|После метода|`Contract.Ensures(result > 0)`|
|**Инвариант (Invariant)**|Согласованность полей объекта|Всегда, после публичных методов|`Contract.Invariant(balance >= 0)`|

⚠️ _Контракты — часть сигнатуры метода_.  
Нельзя **усиливать** контракты в новой версии (нарушит совместимость),  
но можно **ослаблять** (допускается).

---

### 🏗️ Класс `System.Diagnostics.Contracts.Contract`

Главные методы:

```cs
public static class Contract 
{   
// Предусловия   
public static void Requires(bool condition);   
public static void Requires<TException>(bool condition) where TException : Exception;    

// Постусловия   
public static void Ensures(bool condition);   
public static void EnsuresOnThrow<TException>(bool condition) where TException : Exception;    

// Поддержка постусловий   
public static T Result<T>();   
public static T OldValue<T>(T value);   

 // Инварианты   
 public static void Invariant(bool condition);   
  
 // Квантификаторы   
 public static bool ForAll<T>(IEnumerable<T> c, Predicate<T> p);   
 public static bool Exists<T>(IEnumerable<T> c, Predicate<T> p);   
  
 // Проверки и предположения   
 public static void Assert(bool condition);  
 public static void Assume(bool condition); }
```

🧩 Методы с пометкой `[Conditional("CONTRACTS_FULL")]`  
— **выполняются только если задан символ `CONTRACTS_FULL` при компиляции**.  
Методы с пометкой _Always_ работают **всегда**.

---

### ⚙️ Настройка и включение

Чтобы контракты реально выполнялись:

1. В Visual Studio установить флаг **Perform Runtime Contract Checking → Full**.
    
2. Это добавит символ `CONTRACTS_FULL` и активирует инструменты:
    
    - **CCRewrite.exe** — перестраивает IL-код, чтобы постусловия выполнялись _в конце метода_;
        
    - **CCCheck.exe** — выполняет _статическую проверку_;
        
    - **CCRefGen.exe** — создает отдельные сборки с контрактами;
        
    - **CCDocGen.exe** — добавляет контракты в XML-документацию.
        

---

### ⚠️ Нарушение контракта и обработка событий

При нарушении контракта генерируется событие:

`public static event EventHandler<ContractFailedEventArgs> ContractFailed;`

Параметр события:

```cs
public sealed class ContractFailedEventArgs : EventArgs {   public ContractFailureKind FailureKind { get; }   public string Message { get; }   public string Condition { get; }   public Exception OriginalException { get; }    public bool Handled { get; }   public void SetHandled(); // игнорировать нарушение    public bool Unwind { get; }   public void SetUnwind(); // заставить выбросить ContractException }
```

📍Если ни один обработчик не перехватил событие:

- при интерактивной сессии — показывается диалог (Assert);
    
- при службе Windows — вызывается `Environment.FailFast`;
    
- иначе — выбрасывается `ContractException`.
    

---

### 🧮 Пример использования

```cs
public sealed class Item { }  

public sealed class ShoppingCart 
{   
	private List<Item> m_cart = new List<Item>();   
	private decimal m_totalCost = 0;   
	 
	public void AddItem(Item item) 
	{      
		 AddItemHelper(m_cart, item, ref m_totalCost);   
	}    
	 
	 private static void AddItemHelper(List<Item> cart, Item newItem, ref decimal totalCost) 
	 {       
		 // Предусловия       
		 Contract.Requires(newItem != null);       
		 Contract.Requires(Contract.ForAll(cart, s => s != newItem));    
		     
		 // Постусловия       
		 Contract.Ensures(Contract.Exists(cart, s => s == newItem));   
		 Contract.Ensures(totalCost >= Contract.OldValue(totalCost));  
		 Contract.EnsuresOnThrow<IOException>(totalCost == Contract.OldValue(totalCost));
		 
		cart.Add(newItem);       
		totalCost += 1.00M;   
	}   
		         
	[ContractInvariantMethod]   
	private void ObjectInvariant() 
	{       
		Contract.Invariant(m_totalCost >= 0);   
	} 
}
```

---

### ⚠️ Важно помнить

- Методы, используемые в контрактах, **не должны иметь побочных эффектов**.
    
- Методы, используемые в предусловиях, должны быть **не менее доступны**, чем сам метод.
    
- В наследовании **нельзя усиливать предусловия** виртуальных методов.
    
- Для интерфейсов действует то же правило.
    

Если контракт не задан явно, действует **неявный контракт**:

`Contract.Requires(true);`

---

### 🔍 Проверка и инструменты

#### 🧰 CCRewrite.exe

Переписывает IL, чтобы:

- постусловия выполнялись _в конце методов_;
    
- вызывался `ObjectInvariant` после каждого публичного метода.
    

#### 🧰 CCCheck.exe

Проверяет **статически** (без запуска) корректность контрактов.  
Может предупредить о потенциальных сбоях:

`Contract.Assert(s_name.Length >= 1); // предупреждение Contract.Assume(s_name.Length >= 1); // без предупреждения`

`Assume` используется, когда вы **уверены в истинности** условия.

#### 🧰 CCRefGen.exe

Создает _контрактные сборки_ (`YourAssembly.Contracts.dll`)  
→ экономит память и ускоряет выполнение.

#### 🧰 CCDocGen.exe

Добавляет контракты в XML-документ и документацию (через Sandcastle).

---

### 🧭 Итоги

✅ **Контракты кода** — это декларативный способ:

- документировать предположения и гарантии;
    
- автоматически проверять корректность кода;
    
- обнаруживать ошибки ещё на этапе компиляции.
    

🧱 **Основные принципы:**

1. Используйте `Requires` для входных параметров.
    
2. Используйте `Ensures` для гарантий результата.
    
3. Добавляйте `Invariant` для целостности объектов.
    
4. Методы контрактов не должны менять состояние.
    
5. Не усиливайте контракты в наследниках.
    
6. Включайте `CONTRACTS_FULL` для проверки в рантайме.

# 🧨 2 Автоматическое управление памятью (уборка мусора)

## 🗄️ Управляемая куча

### 🔹 Ресурсы и объекты
Любая программа использует ресурсы:
- файлы 📁  
- память 🧠  
- экран 🖥️  
- сетевые соединения 🌐  
- базы данных 🗄️  

В **ООП-среде**:
- каждый **тип** представляет некоторый ресурс;
- для использования ресурса **выделяется память под объект этого типа**.

---

### 🔄 Жизненный цикл ресурса (5 шагов)

1. 🧩 **Выделение памяти**  
   Обычно через оператор `new` в C#.

2. ⚙️ **Инициализация**  
   Выполняется **конструктором**, который задаёт начальное состояние объекта.

3. ▶️ **Использование ресурса**  
   Через обращение к членам типа (методам, полям и т.д.).

4. 🧹 **Очистка состояния ресурса**  
   Требуется **не для всех типов**.

5. ♻️ **Освобождение памяти**  
   ❗ Выполняется **только уборщиком мусора (GC)**.

---

### ⚠️ Проблемы ручного управления памятью (C++)
При неуправляемом программировании часто возникают:
- ❌ **утечки памяти** (забыли освободить);
- ❌ **использование уже освобождённой памяти**.

👉 Эти ошибки:
- трудно воспроизводимы;
- имеют непредсказуемые последствия;
- опаснее большинства других ошибок.

---

### ✅ Преимущества управляемой среды (.NET / CLR)

- При **type-safe коде** (`без unsafe`) повреждение памяти невозможно.
- Утечки памяти **нехарактерны для стандартных сценариев**.
- Основной источник утечек — хранение ненужных объектов в коллекциях.

---

### 🧼 Очистка ресурсов в управляемых типах

- Для **большинства типов** шаг очистки (п.4) **не нужен**.
- Память просто освобождается GC.
- Если тип использует **низкоуровневые ресурсы** (файлы, сокеты, БД):
  - требуется **явная очистка**;
  - обычно реализуется через метод `Dispose`.

📌 Важно:
- `Dispose` позволяет освободить ресурс **раньше GC**;
- реализация таких типов **сложна и нетривиальна**.

---

## 🧱 Выделение памяти в управляемой куче

### 🔹 Managed Heap в CLR
- CLR при старте процесса:
  - резервирует область **виртуального адресного пространства**;
  - создаёт указатель **NextObjPtr** — адрес следующего объекта.

- По мере заполнения:
  - выделяются новые области памяти;
  - предел — **виртуальное адресное пространство процесса**.

📏 Ограничения:
- 🧮 **32-bit процесс**: ~1,5 ГБ  
- 🧮 **64-bit процесс**: ~8 ТБ  

---

### 🆕 Что происходит при `new` #

CLR выполняет следующие шаги:

1. 📐 **Вычисляет размер объекта**  
   - учитываются все поля типа;
   - включая унаследованные от базовых типов.

2. 🧾 **Добавляет системные поля объекта**  
   Каждый объект содержит:
   - указатель на объект-тип;
   - индекс блока синхронизации.

   Размер накладных расходов:
   - 🔹 32-bit: 2 × 32 бита = **8 байт**
   - 🔹 64-bit: 2 × 64 бита = **16 байт**

3. 📦 **Выделяет память**
   - проверяет, хватает ли места;
   - память выделяется по адресу `NextObjPtr`;
   - все байты **обнуляются**;
   - вызывается **конструктор**;
   - `NextObjPtr` сдвигается на конец объекта;
   - `new` возвращает ссылку на объект.

---

### 🧠 Особенности размещения объектов

- Объекты создаются **непрерывно в памяти**.
- Объекты, созданные рядом:
  - часто логически связаны;
  - часто используются вместе.

📌 Пример:
- `FileStream` ➜ затем `BinaryWriter`
- `BinaryWriter` внутри использует `FileStream`

---

### 🚀 Производительность управляемой кучи

Преимущества:
- ⚡ Выделение памяти = **простое увеличение указателя**
- 🧠 Лучшая локальность данных
- 📉 Меньший рабочий набор процесса
- 🧩 Больше объектов помещается в **кэш процессора**
- 🚀 Меньше cache miss → выше скорость работы

---

## ♻️ Алгоритм уборки мусора (Garbage Collection)

### 🚦 Когда запускается уборка мусора
- При выполнении `new` CLR пытается выделить память.
- Если **оставшегося адресного пространства недостаточно**, CLR запускает **уборку мусора**.

⚠️ **Важно (упрощение):**  
На практике GC запускается при заполнении **поколения 0**,  
но для понимания алгоритма считаем, что уборка происходит при заполнении всей кучи.

---

### 🔢 Почему не используется подсчёт ссылок

### 📌 Алгоритм подсчёта ссылок
Используется, например, в **COM**:
- каждый объект хранит **счётчик ссылок**;
- при получении ссылки счётчик увеличивается;
- при потере ссылки — уменьшается;
- при значении `0` объект удаляется.

### ❌ Главная проблема — циклические ссылки
Пример:
- окно ➜ содержит ссылку на дочерний элемент UI;
- дочерний элемент ➜ содержит ссылку на родительское окно.

🔁 В результате:
- счётчики **никогда не становятся равны 0**;
- объекты остаются в памяти, даже если больше не нужны;
- возникает **утечка памяти**.

👉 Из-за этого CLR **не использует подсчёт ссылок**.

---

### 🧠 Алгоритм отслеживания ссылок (Tracing GC)

### 🌱 Корни (Roots)
GC работает **только со ссылочными типами**, потому что:
- только они могут ссылаться на объекты в куче;
- значимые типы содержат данные напрямую.

🔑 **Корнями (roots)** считаются:
- статические поля;
- экземплярные поля объектов;
- аргументы методов;
- локальные переменные.

---

### ⏸️ Этап 1. Остановка потоков
Перед началом GC:
- CLR **приостанавливает все потоки** процесса;
- это предотвращает:
  - обращение к объектам;
  - изменение их состояния во время анализа.

---

### 🏷️ Этап 2. Маркировка (Marking)

### 🔹 Подготовка
- CLR проходит по всем объектам в куче;
- у каждого объекта **сбрасывается бит маркировки**  
  → объект считается *кандидатом на удаление*.

### 🔹 Анализ корней
- CLR перебирает **все корни приложения**:
  - если корень равен `null` → игнорируется;
  - если корень ссылается на объект → объект **маркируется**.

### 🔹 Рекурсивный обход
- После маркировки объекта:
  - CLR проверяет все ссылки внутри него;
  - маркирует объекты, на которые он ссылается;
  - уже маркированные объекты **не обрабатываются повторно**  
    → защита от бесконечных циклов.

📌 Результат:
- **маркированные объекты** — достижимы из кода приложения;
- **немаркированные объекты** — недостижимы и считаются мусором.

---

### 📦 Этап 3. Сжатие (Compacting)

После определения «живых» объектов начинается фаза **сжатия**.

#### 🔹 Что делает CLR
- перемещает все **немусорные объекты вниз** в памяти;
- размещает их **непрерывно**.

#### 🎯 Преимущества сжатия
- 📉 уменьшается рабочий набор процесса;
- 🚀 повышается производительность доступа к объектам;
- 🧹 свободная память становится непрерывной;
- ❌ устраняется фрагментация памяти.

---

### 🔗 Обновление ссылок
После перемещения объектов:
- все корни всё ещё указывают на **старые адреса**;
- это недопустимо → приведёт к повреждению памяти.

✔️ Решение:
- CLR **корректирует все ссылки**;
- каждый корень сдвигается на то же количество байт,
  на которое был перемещён объект.

👉 В итоге каждый корень по-прежнему ссылается на **тот же объект**,  
но уже по **новому адресу**.

---

### ▶️ Завершение GC
- `NextObjPtr` указывает на первый свободный адрес после «живых» объектов;
- потоки приложения **возобновляют выполнение**;
- приложение работает так, будто GC не происходил.

---

### 💥 Недостаток памяти
Если после GC:
- свободной памяти всё равно недостаточно;
- и невозможно выделить новый сегмент,

➡️ оператор `new` выбрасывает **OutOfMemoryException**.

Обычно:
- приложения **не обрабатывают** это исключение;
- процесс завершается;
- Windows освобождает всю его память.

---

### 📚 Ключевые выводы для программиста

### ✅ Что гарантирует GC
- 🧼 **утечки объектов исключены**  
  (все недостижимые от корней объекты будут удалены);
- 🛡️ **невозможно обратиться к освобождённому объекту**;
- ❌ исключено повреждение памяти.

---

### ⚠️ Важное предупреждение про статические поля

- **Статические поля** хранят ссылки:
  - до выгрузки домена приложения;
  - фактически — бессрочно.

🚨 Частая причина утечек памяти:
- статическое поле содержит ссылку на коллекцию;
- в коллекцию постоянно добавляются элементы;
- коллекция и её элементы **никогда не удаляются**.

👉 **Рекомендация:**  
по возможности **избегать статических полей**, особенно хранящих коллекции.


## 🐞 Уборка мусора и отладка — в чём суть

### 🧠 Ключевая идея
👉 **Объект может быть уничтожен GC сразу после того, как становится недостижимым**,  
даже если метод, в котором он создан, ещё не завершился.

Это особенно важно:
- при **отладке**;
- при работе с объектами, которые **что-то делают сами** (например, `Timer`).

---

### ⏱️ Неочевидное поведение на примере `Timer`

### 🔹 Ожидание
- Создаём `Timer`
- Он должен вызывать `TimerCallback` каждые 2 секунды
- `Main` ждёт `Console.ReadLine()`

👉 Кажется, что таймер должен работать всё это время.

### 🔹 Реальность (без /debug)
- `TimerCallback` вызывается **только один раз**.

---

### ❓ Почему так происходит

- GC запускается вручную (`GC.Collect()`);
- GC считает **все объекты мусором**, пока не докажет обратное;
- CLR проверяет **корни**;
- переменная `t` **больше не используется** после создания таймера;
- значит:
  - `t` **не считается корнем**;
  - объект `Timer` **недостижим**;
  - GC **удаляет его**;
  - таймер прекращает работу.

📌 Важно:  
**время жизни объекта ≠ время жизни переменной в коде**,  
а зависит от того, **считает ли JIT переменную корнем**.

---

### 🧪 Проблема при отладке

- GC может удалить объект **прямо во время отладки**;
- при попытке посмотреть его в `Quick Watch`:
  - объекта уже нет;
  - отладчик ничего не покажет.

😬 Это крайне неудобно для разработчика.

---

### 🛠️ Как /debug меняет поведение

При компиляции с ключом `/debug`:

- компилятор добавляет атрибут  
  `DebuggableAttribute(DisableOptimizations)`;
- JIT **отключает оптимизации**;
- JIT **искусственно продлевает жизнь всех корней**  
  до конца метода.

👉 В примере:
- переменная `t` считается корнем до выхода из `Main`;
- объект `Timer` **не удаляется GC**;
- `TimerCallback` вызывается многократно.

⚠️ Ключ `/optimize+` снова включает оптимизации — его использовать нельзя.

---

### 🚨 Опасный вывод
Можно написать программу, которая:
- ✔️ работает в режиме отладки;
- ❌ ломается в релизе.

👉 Такая программа **бесполезна**.

---

### ❌ Почему `t = null` не спасает

Интуитивное решение:
```csharp
t = null;
```

Но:

- JIT — **оптимизирующий компилятор**;
    
- присваивание `null` локальной переменной:
    
    - эквивалентно отсутствию ссылки;
        
    - полностью **выбрасывается при оптимизации**.
        

👉 Поведение не меняется.
### ✅ Правильное решение — `Dispose`

Корректный подход:

`t.Dispose();`

Почему это работает:

- объект **должен быть жив**, чтобы вызвать `Dispose`;
    
- JIT **обязан сохранить ссылку** до этой точки;
    
- GC **не может удалить объект раньше**.
    

🧩 Парадокс:

> Явно указывая момент уничтожения объекта,  
> мы **продлеваем его жизнь до этого момента**.

---

### 🧠 Главные выводы (must-know для собеседований)

- 🧹 GC может уничтожить объект **раньше, чем кажется**;
    
- ⏳ время жизни объекта определяется:
    
    - не областью видимости;
        
    - а **использованием переменной с точки зрения JIT**;
        
- 🐞 режим `/debug`:
    
    - меняет поведение GC и JIT;
        
    - **маскирует ошибки**, которые появятся в релизе;
        
- ❌ `= null` — не способ управлять временем жизни;
    
- ✅ `Dispose` — корректный способ явно управлять ресурсами.
    

---

### 📝 Важное примечание

- Не стоит бояться, что **все объекты будут удаляться слишком рано**.
    
- `Timer` — **особый случай**:
    
    - он сам инициирует выполнение кода;
        
    - большинство объектов так себя не ведут.
        

📌 Например:

- `string` в куче просто существует;
    
- его наличие **не вызывает побочных эффектов**.
    

👉 Пример с `Timer` нужен, чтобы:

- показать работу **корней**;
    
- объяснить связь **GC, JIT и отладчика**.
    

⛔ В реальных приложениях:

- время жизни обычных объектов
    
- **корректно управляется автоматически**.

## 🧬 Поколения в уборке мусора (Generational GC)

### 🧠 Суть подхода
Поколенческий (эфемерный) GC основан на трёх эмпирически подтверждённых идеях:

1. 👶 **Молодые объекты живут недолго**
2. 🧓 **Старые объекты, скорее всего, будут жить дальше**
3. ⚡ **Убирать часть кучи быстрее, чем всю кучу целиком**

👉 Поэтому GC **чаще и быстрее** проверяет молодые объекты и **реже** — старые.

---

### 🗂️ Какие бывают поколения
В управляемой куче **всего 3 поколения**:

- **Поколение 0 (Gen 0)** — только что созданные объекты  
- **Поколение 1 (Gen 1)** — объекты, пережившие 1 уборку  
- **Поколение 2 (Gen 2)** — объекты, пережившие ≥ 2 уборок  

📌 Поколений больше **не существует**  
`GC.MaxGeneration == 2`

---

### 🌱 Поколение 0 — стартовая точка

- После запуска приложения куча пуста
- **Все новые объекты попадают в Gen 0**
- Для Gen 0 задан **пороговый размер**

#### 🔔 Когда запускается GC
Если при `new`:
- размер Gen 0 превышает порог  
➡️ начинается уборка мусора

---

### ♻️ Первая уборка мусора (Gen 0)

- GC проверяет **только поколение 0**
- Недостижимые объекты → удаляются
- Выжившие объекты:
  - **сжимаются**
  - **переводятся в поколение 1**

📌 После GC:
- **Gen 0 пуст**
- новые объекты снова создаются в Gen 0

---

### 🔁 Повторные сборки Gen 0

- Приложение продолжает создавать новые объекты
- В Gen 1 постепенно появляется **мусор**
- Но GC **игнорирует Gen 1**, пока:
  - его размер **не превышает порог**

👉 Почему?
- Старые объекты с высокой вероятностью ещё нужны
- Проверка Gen 1 дала бы мало выгоды, но стоила бы времени

---

### ⚡ Почему GC в Gen 0 очень быстрый

- Проверяется **малая часть кучи**
- Старшие поколения:
  - **не сканируются**
  - их внутренние ссылки **игнорируются**

⏱️ По тестам Microsoft:
- уборка Gen 0 занимает **< 1 мс**
- цель — не дольше обычной **page fault**

---

### 🔗 Старые объекты и ссылки на новые

### ❓ Проблема
Что если:
- объект из Gen 1 или Gen 2
- ссылается на объект из Gen 0?

#### ✅ Решение — write barrier
- JIT вставляет **барьер записи**
- При изменении ссылочного поля:
  - отмечается соответствующий участок памяти (card table)
- GC проверяет **только изменённые старые объекты**

📉 Минус:
- запись в ссылочные поля объектов Gen 1/2 **медленнее**
- но это цена за быстрый GC

---

### 📈 Рост поколения 1

- После каждой уборки:
  - выжившие из Gen 0 → переходят в Gen 1
- Мусор в Gen 1 **может накапливаться**
- Он **не удаляется**, пока Gen 1 не превысит порог

---

### 🧹 Когда чистится поколение 1

GC начинает проверять **Gen 0 + Gen 1**, если:
- суммарный размер Gen 1 **превысил порог**

Результат:
- мусор в Gen 1 удаляется
- выжившие из:
  - Gen 0 → переходят в Gen 1
  - Gen 1 → переходят в Gen 2

---

### 🧱 Поколение 2 — «долгожители»

- Объекты, пережившие ≥ 2 уборок
- Проверяются **реже всего**
- Обычно содержат:
  - кэши
  - глобальные структуры
  - долго живущие данные

📌 GC может выполнять **полную уборку (Gen 0 + 1 + 2)**:
- если памяти не хватает
- перед `OutOfMemoryException`

---

### 🧠 Самонастраивающийся GC

GC **динамически подстраивается** под приложение:

#### Если в Gen 0:
- почти всё — мусор  
➡️ порог **уменьшается**  
➡️ GC запускается чаще, но быстро

#### Если в Gen 0:
- много выживших  
➡️ порог **увеличивается**  
➡️ GC реже, но освобождает больше памяти

То же самое происходит и с Gen 1 / Gen 2.

👉 Итог:  
**GC автоматически адаптируется под модель памяти приложения**

---

### 🖥️ Почему это идеально для UI и серверов

### 🎨 UI-приложения
- поток ждёт событий
- пользовательский ввод → создаются временные объекты
- после обработки → они становятся мусором

### 🌐 Серверные приложения
- пул потоков
- каждый запрос:
  - создаёт временные объекты
  - после ответа клиенту → всё выбрасывается

➡️ **Поколенческий GC здесь максимально эффективен**

---

### 📊 Наблюдение за GC (идея)

Можно отслеживать:
- уборку Gen 0 и Gen 2
- частоту сборок
- объём выделенной памяти

👉 Это позволяет:
- анализировать поведение приложения
- лучше понимать нагрузку на память
- выявлять проблемы архитектуры

(Пример — класс `GCNotification`)

---

### 🎯 Главное для собеседований

- GC в .NET — **поколенческий**
- Всего **3 поколения: 0, 1, 2**
- Новые объекты → Gen 0
- Выжившие → продвигаются вверх
- GC:
  - чаще всего чистит Gen 0
  - редко — Gen 2
- Пороги **динамические**
- Старые объекты обычно не проверяются
- Write barrier нужен для ссылок из старых поколений в новые

👉 **Это ключ к высокой производительности GC**


## 🧹 Запуск уборки мусора (GC Triggers)

### 🧠 Основная причина
CLR **чаще всего запускает GC**, когда:
- **поколение 0** достигает своего **порогового размера**

👉 Это нормальный и ожидаемый сценарий.

---

### 🔔 Другие причины запуска GC

#### 1️⃣ Явный вызов `GC.Collect()`
- Разработчик **принудительно** запускает GC
- Microsoft **не рекомендует** использовать
- Допустимо в редких случаях (рассматриваются отдельно)

📌 Минус:  
нарушает эвристики GC → может **сильно ухудшить производительность**

---

#### 2️⃣ Нехватка памяти в системе (Windows)
- CLR следит за состоянием памяти через Win32:
  - `CreateMemoryResourceNotification`
  - `QueryMemoryResourceNotification`
- Если Windows сообщает о дефиците памяти:
  - CLR запускает GC
  - цель:
    - удалить неиспользуемые объекты
    - уменьшить рабочий набор процесса

---

#### 3️⃣ Выгрузка домена приложения
- При выгрузке `AppDomain`:
  - CLR выполняет **полную уборку мусора**
  - очищаются **все поколения (0, 1, 2)**

📌 Домены приложений — отдельная тема (гл. 22)

---

#### 4️⃣ Завершение работы CLR
CLR завершает работу при **нормальном завершении процесса**:

- CLR считает, что:
  - **корневых ссылок нет**
- Всем объектам:
  - даётся возможность выполнить очистку (finalize)
- Но:
  - **сжатие и освобождение памяти не выполняется**
  - Windows всё равно освободит всю память процесса

⚠️ Это не происходит при аварийном завершении (например, через Task Manager)

---

## 🧱 Большие объекты (Large Object Heap, LOH)

### 📏 Что считается большим объектом
- **≥ 85 000 байт**
- Все предыдущие примеры касались **малых объектов**

---

### 🗂️ Особенности работы с большими объектами

#### 🔹 1. Отдельная область памяти
- Большие объекты размещаются:
  - в **отдельной части адресного пространства**
  - не в обычной управляемой куче

---

#### 🔹 2. Нет сжатия
- Большие объекты **не перемещаются**
- Причина:
  - перемещение слишком дорого по CPU
- Следствие:
  - возможна **фрагментация**
  - в крайних случаях → `OutOfMemoryException`

📌 В будущих версиях CLR возможна поддержка сжатия LOH

---

#### 🔹 3. Всегда поколение 2
- Все большие объекты:
  - **автоматически относятся к Gen 2**
- Поэтому:
  - их нужно создавать **только для долгоживущих данных**

❌ Короткоживущие большие объекты:
- вызывают частые сборки Gen 2
- резко **ухудшают производительность**

---

### 📦 Типичные примеры больших объектов
- большие строки:
  - XML
  - JSON
- большие массивы байтов:
  - буферы чтения из файла
  - сетевые буферы
  - I/O операции

---

### 🫥 Прозрачность для разработчика
- Все механизмы:
  - полностью **прозрачны**
  - не требуют специального кода
- О них можно:
  - **не думать**, пока всё работает нормально

🚨 Проблемы проявляются только при:
- фрагментации памяти
- `OutOfMemoryException`
- неожиданно частых GC Gen 2

---


## 🧹 Режимы уборки мусора в CLR

### ⚙️ Общая идея
- Режим GC **выбирается при запуске CLR**
- ❗ Не может быть изменён до завершения процесса
- Режим влияет на:
  - паузы приложения
  - использование CPU
  - потребление памяти
  - масштабируемость

---

### 🖥️ Основные режимы GC

#### 1️⃣ Режим рабочей станции (Workstation GC)
🔹 Назначение:
- Клиентские приложения (UI, desktop)

🔹 Характеристики:
- Минимизирует **паузы потоков**
- Не раздражает пользователя подвисаниями
- Предполагает наличие **других приложений** в системе
- Экономно использует CPU

📌 Используется **по умолчанию**
(с включённой параллельной уборкой)

---

#### 2️⃣ Режим сервера (Server GC)
🔹 Назначение:
- Серверные приложения (ASP.NET, SQL Server)

🔹 Характеристики:
- Считает, что машина **выделена под одно приложение**
- Максимально использует ресурсы процессора
- Управляемая куча:
  - разбивается на **несколько сегментов**
  - по одному на **каждый процессор**
- Используется:
  - **один GC-поток на процессор**
  - сборка выполняется **параллельно**

📌 Эффективен только:
- на **многопроцессорных** системах
- при равномерной нагрузке потоков

⚠️ На однопроцессорной машине:
- всегда используется Workstation GC

---
## 🧠 Программное управление уборщиком мусора

- `GC.MaxGeneration` → всегда **2**
- Принудительный GC: `GC.Collect(gen, mode, blocking)`
 
*GCCollectionMode*:

Default — как обычный GC.Collect

Forced — всегда собирает

Optimized — только если есть реальный эффект

Главное:
❌ Обычно GC.Collect() не нужен

✅ Допустим после разовых тяжёлых операций

Используют для уменьшения памяти, а не ускорения

## 🧹Освобождение ресурсов с помощью механизма финализации

### Зачем вообще нужна финализация
- **GC освобождает только управляемую память**, но не знает ничего о системных ресурсах.
- Некоторые типы используют **неуправляемые ресурсы**:
  - файлы (`FileStream`)
  - мьютексы (`Mutex`)
  - сокеты, сетевые соединения и т. д.
- Если объект будет собран GC без явной очистки:
  - память вернётся в managed heap
  - **системный ресурс будет утерян (утечка)**

👉 Поэтому CLR поддерживает **механизм финализации (finalization)** — возможность корректно освободить системные ресурсы *перед* освобождением памяти.

---

### Метод Finalize и синтаксис `C#`
- В `System.Object` определён защищённый виртуальный метод `Finalize`.
- Если объект становится недоступным:
  - GC вызывает `Finalize`, **если он переопределён**.
- В C# используется специальный синтаксис:

```cs
~SomeType() { /* cleanup */ }
```
### Важно

- Это **НЕ деструктор в смысле C++**.
    
- **Нет детерминированного уничтожения**:
    
    - CLR сам решает, _когда_ вызывать `Finalize`
        
    - порядок вызова не гарантирован
        

⚠️ Ошибка разработчиков с C++-бэкграундом — ожидание немедленного уничтожения.

---

### Цена финализации

Финализация — **дорогой и опасный механизм**:

#### 1. Объект живёт дольше

- Финализируемый объект **переживает GC**:
    
    - переводится в следующее поколение
        
- Все объекты, на которые он ссылается, **тоже продлевают жизнь**
    

👉 **Финализацию следует избегать**, особенно у объектов с ссылочными полями.

---

#### 2. Непредсказуемость

- Нельзя знать:
    
    - **когда** вызовется `Finalize`
        
    - **в каком порядке**
        
- Нельзя безопасно обращаться:
    
    - к объектам с `Finalize`
        
    - к статическим методам (они могут использовать уже финализированные объекты)
        

---

#### 3. Поток финализации

- CLR использует **специальный высокоприоритетный поток**.
    
- Если `Finalize`:
    
    - зависает
        
    - входит в бесконечный цикл
        
    - блокируется навсегда  
        → **GC перестаёт освобождать память финализируемых объектов**
        

❌ Необработанное исключение в `Finalize` → **завершение процесса**

---

### Вывод Рихтера по Finalize

- `Finalize` предназначен **ТОЛЬКО для освобождения системных ресурсов**
    
- Использовать его напрямую **не рекомендуется**
    
- Вместо этого — **SafeHandle и FCL-инфраструктура**
    

---

### SafeHandle — правильный путь

Если управляемый тип использует системный ресурс:

👉 **Нужно использовать `System.Runtime.InteropServices.SafeHandle`**

### Общая идея

- `SafeHandle`:
    
    - реализует `IDisposable`
        
    - имеет финализацию
        
    - безопасен при работе с GC и interop
        
- Производный класс:
    
    - хранит `IntPtr handle`
        
    - переопределяет:
        
        - `ReleaseHandle`
            
        - `IsInvalid`
            

---

### Почему SafeHandle особенный

`SafeHandle` наследуется от `CriticalFinalizerObject`, что даёт 3 ключевые гарантии:

#### 1. Гарантированная JIT-компиляция финализаторов

- Все финализаторы компилируются **при первом создании объекта**
    
- Иначе:
    
    - при нехватке памяти финализатор может не выполниться
        
    - → утечка ресурсов
        

---

#### 2. Порядок финализации

- Финализаторы `CriticalFinalizerObject` вызываются **ПОСЛЕ обычных**
    
- Это позволяет:
    
    - управляемым объектам (например `FileStream`)
        
    - безопасно обращаться к системным ресурсам в `Finalize`
        

---

#### 3. Финализация при аварийном завершении AppDomain

- Даже если:
    
    - хост (ASP.NET, SQL Server) аварийно выгружает домен
        
- Системные ресурсы **всё равно будут освобождены**
    

---

### SafeHandleZeroOrMinusOneIsInvalid

- Удобный базовый класс:
    
    - `handle == 0` или `-1` → недействителен
        
- От него наследуются:
    
    - `SafeFileHandle`
        
    - `SafeRegistryHandle`
        
    - `SafeWaitHandle`
        
    - `SafeMemoryMappedViewHandle`
        

Пример:

`protected override Boolean ReleaseHandle() {     return Win32Native.CloseHandle(handle); }`

👉 Разные классы нужны **ради типобезопасности**, а не логики.

---

### SafeHandle и interop (очень важно)

#### Проблема IntPtr

- Если P/Invoke возвращает `IntPtr`:
    
    - возможен `ThreadAbortException`
        
    - дескриптор не присвоится
        
    - **утечка ресурса навсегда**
        

#### Решение

- Возвращать `SafeHandle` напрямую:
    

`[DllImport("Kernel32")] static extern SafeWaitHandle CreateEvent(...);`

✔️ CLR:

- создаёт `SafeHandle`
    
- присваивает дескриптор **в неуправляемом коде**
    
- исключение не может прервать процесс
    

---

### Безопасность: защита от повторного использования дескрипторов

- `SafeHandle` ведёт **подсчёт ссылок**
    
- CLR:
    
    - увеличивает счётчик при передаче в native-код
        
    - уменьшает после возврата
        
- Пока счётчик > 0:
    
    - **ресурс нельзя освободить**
        

👉 Защита от race condition и атак reuse-handle.

### Опасные методы

- `DangerousAddRef`
    
- `DangerousRelease`
    
- `DangerousGetHandle`
    

⚠️ Использовать только при необходимости и с пониманием рисков.

---

### CriticalHandle

- Аналог `SafeHandle`, **но без подсчёта ссылок**
    
- Быстрее, но:
    
    - **менее безопасен**
        
- В FCL почти не используется
    

👉 Использовать **только если производительность важнее безопасности**

## 🐞 Типы, использующие системные ресурсы

### Как FileStream работает с системными ресурсами
- `FileStream` — типичный пример класса, использующего системный ресурс.
- При создании:
  - вызывается Win32 `CreateFile`
  - дескриптор сохраняется в **SafeFileHandle**
  - `SafeFileHandle` хранится как закрытое поле в `FileStream`
- `FileStream` дополнительно предоставляет:
  - свойства (`Length`, `Position`, `CanRead`)
  - методы (`Read`, `Write`, `Flush`)

👉 `FileStream` **сам не владеет дескриптором напрямую**, он делегирует это `SafeHandle`.

---

### Проблема: удаление открытого файла
Пример кода:
- создаём файл
- записываем в него
- пытаемся удалить

Результат:
- `File.Delete` генерирует `IOException`
- причина: файл **всё ещё открыт**

#### Почему иногда «случайно работает»
- Если между `Write` и `Delete` случился GC:
  - финализатор `SafeFileHandle` закрывает файл
  - `Delete` проходит успешно
- Вероятность крайне мала → **нельзя полагаться на GC**

👉 Финализация **не предназначена для управления временем освобождения ресурсов**.

---

### IDisposable — управление жизненным циклом ресурса
- Типы, позволяющие управлять ресурсами, реализуют:
```cs
public interface IDisposable {
  void Dispose();
}
```

### Важное правило проектирования

> **Если класс содержит поле, реализующее `Dispose`, сам класс тоже должен реализовать `IDisposable`.**

- `Dispose` внешнего объекта:
    
    - вызывает `Dispose` у внутренних ресурсов
        
- Это даёт пользователю контроль над моментом освобождения ресурса
    

---

### FileStream и Dispose

- `FileStream` реализует `IDisposable`
    
- Его `Dispose`:
    
    - вызывает `Dispose` у `SafeFileHandle`
        
    - закрывает файл **немедленно**
        

Исправленный код:

`fs.Write(...); fs.Dispose(); File.Delete("Temp.dat"); // всегда работает`

---

### Dispose ≠ уничтожение объекта

- Вызов `Dispose`:
    
    - **освобождает системные ресурсы**
        
    - **НЕ удаляет объект из managed heap**
        
- Объект остаётся:
    
    - его методы можно вызывать
        
    - но они должны корректно реагировать
        

---

### Поведение после Dispose

- Вызов методов после освобождения ресурса:
    
    - генерирует `ObjectDisposedException`
        
- Пример:
    
    - повторный `Write` → исключение
        
- Память при этом **не повреждается**
    

---

### Требования к типам, реализующим IDisposable

### Обязательные правила

- После `Dispose`:
    
    - **все методы и свойства** должны бросать  
        `ObjectDisposedException`
        
- Повторный вызов `Dispose`:
    
    - **не должен** бросать исключения
        
    - должен просто возвращать управление
        

---

### Важное предупреждение Рихтера о Dispose

⚠️ **В общем случае Рихтер не рекомендует вызывать `Dispose` без крайней необходимости.**

Причины:

- GC сам:
    
    - определяет недоступность объекта
        
    - освобождает ресурсы корректно
        
- Вызов `Dispose` — заявление:
    
    > «Я точно знаю, что объект больше не нужен»
    

Часто это **неправда**:

- объект может быть:
    
    - сохранён другим методом
        
    - использован другим кодом
        
- результат — `ObjectDisposedException`
    

👉 Вызывать `Dispose` стоит **только там, где момент освобождения ресурса гарантированно известен**  
(например, перед удалением файла).

---

### Dispose и многопоточность

- `Dispose` **не обязан быть потокобезопасным**
    
- Несколько потоков могут вызвать `Dispose` одновременно
    
- По правилам проектирования:
    
    - `Dispose` вызывается **только если объект точно не используется**
        

👉 Ответственность лежит на вызывающем коде.

---

### Dispose и finally

Если используется явный `Dispose`, его **нужно вызывать в `finally`**:

- это гарантирует освобождение ресурса
    
- даже при исключениях
    

Шаблон:

`FileStream fs = new FileStream(...); try {   ... } finally {   fs.Dispose(); }`

---

### Инструкция using

C# предоставляет синтаксический сахар:

`using (FileStream fs = new FileStream(...)) {   ... }`

### Что делает `using`

- Компилятор:
    
    - генерирует `try / finally`
        
    - в `finally` вызывает `Dispose`
        
- Использовать можно **только с типами, реализующими `IDisposable`**
    

👉 `using` — **рекомендуемый способ** работы с временными системными ресурсами.

---

### Итог главы

- Системные ресурсы **нельзя оставлять на усмотрение GC**
    
- `IDisposable` даёт контроль над временем освобождения
    
- `Dispose`:
    
    - освобождает ресурс
        
    - не удаляет объект
        
- Использовать `Dispose` нужно **осознанно**
    
- `using` — безопасный и идиоматичный способ

---

## 📘 Интересные аспекты зависимостей

#### 🧩 Работа с `FileStream` и `StreamWriter`

- `FileStream` — открывает файл для чтения/записи байтов.
    
    - Использует **буферизацию** → данные записываются в файл не сразу.
        
- Для записи строк/символов используют `StreamWriter`, который работает поверх `Stream`.
    

✅ Пример работы:

- `StreamWriter` хранит ссылку на `FileStream`.
    
- `StreamWriter` имеет **свой буфер**, который потом записывает в `Stream`.
    

#### ♻️ Освобождение ресурсов

- После записи нужно вызвать `Dispose()` или использовать `using`.
    
- `StreamWriter.Dispose()`:
    
    - Сбрасывает буфер.
        
    - Закрывает связанный `FileStream`.
        
- `FileStream.Dispose()` можно не вызывать вручную — это сделает `StreamWriter`.
    

#### ⚠️ Почему нельзя надеяться только на сборщик мусора

- GC может вызвать финализацию объектов **в случайном порядке**.
    
- Если сначала закроется `FileStream`, а затем `StreamWriter` попробует записать данные → возникнет ошибка.
    
- Поэтому:
    
    - `StreamWriter` **не имеет финализатора**.
        
    - Если забыть вызвать `Dispose()` → данные могут потеряться.
        
    - Это сделано специально, чтобы разработчик заметил проблему.
        

#### 🐞 Отладка потери данных

- В .NET есть **Managed Debugging Assistants (MDA)**.
    
- Они могут обнаруживать потерю буферизованных данных (`StreamWriterBufferedDataLost`).

## 📘 Дополнительные возможности сборщика мусора при работе с системными ресурсами

#### 🧠 Проблема: маленький объект — большой системный ресурс

- Управляемый объект может занимать мало памяти.
    
- Но связанный системный ресурс (например, изображение) может занимать мегабайты.
    
- GC ориентируется только на управляемую память → может поздно запускаться.
    

#### 📢 Решение: уведомление GC о реальной нагрузке

Используются методы:

- `GC.AddMemoryPressure(bytes)` — сообщает о выделении большой системной памяти.
    
- `GC.RemoveMemoryPressure(bytes)` — сообщает об освобождении памяти.
    

👉 Это помогает GC запускаться чаще при высокой нагрузке.

---

#### 🔒 Ограниченные системные ресурсы

Иногда ресурсы ограничены по количеству:

- дескрипторы устройств;
    
- открытые файлы;
    
- другие системные объекты.
    

Если превысить лимит → возникнет исключение.

---

#### 🧮 Класс `HandleCollector`

Используется для отслеживания количества ограниченных ресурсов.

Основные возможности:

- Ведёт счётчик используемых ресурсов.
    
- Когда ресурсов становится много → запускает GC.
    

Основные методы:

- `Add()` — ресурс выделен.
    
- `Remove()` — ресурс освобождён.
    
- `Count` — текущее количество ресурсов.
    

---

#### ⚠️ Принудительный запуск GC

- Обычно вызывать `GC.Collect()` не рекомендуется (ухудшает производительность).
    
- Но `AddMemoryPressure` и `HandleCollector` могут делать это:
    
    - чтобы избежать нехватки ограниченных ресурсов;
        
    - лучше медленнее работать, чем аварийно завершиться.
        

---

### 🧪 Демонстрация в коде

- `BigNativeResource`:
    
    - Сообщает GC о большом объёме системной памяти.
        
    - Чем больше размер → тем чаще запускается GC.
        
- `LimitedResource`:
    
    - Использует `HandleCollector`.
        
    - Когда объектов становится много → GC вызывается чаще.

## 📘  Внутренняя реализация финализации (сделать конспект)


### Общая идея
**Финализация** — это не просто вызов метода перед удалением объекта.  
На самом деле CLR использует **несколько внутренних структур** и **отдельный поток**, а освобождение памяти происходит **не за один GC**.

---

### Создание объекта с финализатором

1. Оператор `new`:
   - выделяет память в **управляемой куче**
2. Если у типа **переопределён** метод финализации:
   - **до вызова конструктора**
   - указатель на объект **добавляется в список финализации**

#### 🧠 Важно
> Если метод финализации **унаследован от `System.Object`**,  
> то **он игнорируется CLR**  
> ➜ объект **НЕ попадает** в список финализации  
>
> 🔹 Финализатор **обязательно должен быть переопределён**

---

### Внутренние структуры CLR

### 1. Список финализации (Finalization List)
- содержит ссылки на объекты:
  - **у которых есть финализатор**
  - и **которые ещё не финализированы**
- управляется **уборщиком мусора**

### 2. Очередь на финализацию (F-Reachable Queue)
- содержит ссылки на объекты:
  - **готовые к вызову финализатора**
- считается **корнем GC**
- объекты в ней:
  - **достижимы**
  - **не считаются мусором**

---

### Первая уборка мусора (GC #1)

#### Шаг 1. Поиск мусора
GC определяет объекты, **недостижимые из корней приложения**

#### Шаг 2. Работа со списком финализации
- если объект:
  - недостижим
  - **и есть в списке финализации**
- GC:
  - **удаляет ссылку из списка финализации**
  - **перемещает её в очередь на финализацию**

#### Результат
- 🗑️ Объекты **без финализатора**:
  - память освобождается сразу
- ⏸️ Объекты **с финализатором**:
  - память **НЕ освобождается**
  - объект **временно “воскрешается”**

---

### Почему объекты «воскрешаются»

- Очередь на финализацию — это **корень**
- Объект в очереди:
  - снова считается **достижимым**
  - **перестаёт быть мусором**

📌 Это означает:
> Объект может быть признан мусором,  
> а затем **снова стать живым**

---

### Рекурсивная маркировка

- Если объект попал в очередь:
  - GC **маркирует и все объекты**,  
    на которые он ссылается
- Эти объекты:
  - тоже **переживают уборку мусора**
- Обычно такие объекты:
  - **перемещаются в более старшее поколение**

---

### Поток финализации

#### Особенности
- В CLR есть **отдельный высокоприоритетный поток**
- Он:
  - простаивает, если очередь пуста
  - при появлении элементов:
    - последовательно вызывает финализаторы

#### Ограничения для финализатора
🚫 Нельзя писать код, который:
- зависит от конкретного потока
- использует локальную память потока
- предполагает последовательный вызов

📌 В будущем возможно:
- **несколько потоков финализации**
- поэтому нельзя рассчитывать на порядок вызова

---

### Вторая уборка мусора (GC #2)

После выполнения финализаторов:
- очередь на финализацию пуста
- на объекты:
  - не указывают корни
  - не указывает очередь

➡️ Объекты **окончательно становятся мусором**  
➡️ Память **освобождается**

---

### Ключевой вывод 

> 🔥 **Объекты с финализатором освобождаются ТОЛЬКО ПОСЛЕ ДВУХ GC**

1. Первый GC:
   - объект признаётся мусором
   - но переносится в очередь финализации
2. Второй GC:
   - объект уже финализирован
   - память освобождается

⚠️ Иногда требуется **больше двух GC**,  
потому что объект может перейти в старшее поколение.

---

### Краткая схема жизненного цикла

1. `new` → объект в куче  
2. Есть финализатор → в список финализации  
3. GC #1:
   - объект недостижим
   - перенос в очередь на финализацию
   - объект «воскрешается»
4. Поток CLR:
   - вызывает финализатор
5. GC #2:
   - объект удаляется окончательно

---

## 📘 Мониторинг и контроль времени жизни объектов (сделать конспект)

### Общая идея
CLR предоставляет механизм **явного мониторинга и управления временем жизни объектов**  
через **таблицу GC-дескрипторов (GC Handle Table)**, отдельную для каждого *домена приложения*.

Таблица:
- изначально **пуста**
- содержит элементы вида:
  - указатель на объект в управляемой куче
  - флаг, определяющий способ контроля/мониторинга

Работа с таблицей осуществляется через тип:
`System.Runtime.InteropServices.GCHandle`

---

### Тип GCHandle

#### Назначение
`GCHandle` — это **обертка над элементом таблицы GC-дескрипторов**,  
позволяющая:
- отслеживать существование объекта
- управлять временем его жизни
- (при необходимости) фиксировать его в памяти

#### Ключевая особенность
> `GCHandle` — **значимый тип**, содержащий `IntPtr`,  
> указывающий **на индекс в таблице GC-дескрипторов**

---

### Основные члены GCHandle (концептуально)

#### Создание записи
- `Alloc(object value)`
- `Alloc(object value, GCHandleType type)`

#### Освобождение
- `Free()` — удаляет элемент из таблицы и делает GCHandle недействительным

#### Доступ к объекту
- `Target` — получить / заменить ссылку на объект
- `IsAllocated` — проверка, активен ли GCHandle

#### Для фиксированных объектов
- `AddrOfPinnedObject()` — возвращает **адрес объекта в памяти**

---

### Тип GCHandleType

```cs
public enum GCHandleType {
  Weak = 0,
  WeakTrackResurrection = 1,
  Normal = 2,
  Pinned = 3
}
```
### Значение флагов GCHandleType

#### Weak — слабая ссылка

- **Только мониторинг**
    
- Позволяет определить:
    
    - стал ли объект недоступен приложению
        
- ⚠️ Финализатор:
    
    - **мог выполниться**
        
    - **мог не выполниться**
        
- Объект **может всё ещё находиться в памяти**
    

---

#### WeakTrackResurrection — слабая ссылка с отслеживанием воскрешения

- Мониторинг **после финализации**
    
- Если `Target == null`:
    
    - финализатор **точно выполнен**
        
    - память **освобождена**
        
- 📌 Практически **не используется**
    

---

#### Normal — управление временем жизни

- Объект:
    
    - **не удаляется GC**
        
    - даже если на него нет корней
        
- GC:
    
    - **может перемещать (сжимать) объект**
        
- Используется:
    
    - при передаче ссылки в неуправляемый код
        
- Значение по умолчанию для `Alloc(object)`
    

---

#### Pinned — управление + фиксация

- Объект:
    
    - **не удаляется**
        
    - **не перемещается**
        
- GC **запрещено сжимать память**, занятую объектом
    
- Используется:
    
    - при передаче **адреса памяти** в неуправляемый код
        

⚠️ Чрезмерное использование `Pinned`:

- ухудшает работу GC
    
- увеличивает фрагментацию памяти
    

---

### Как GC работает с таблицей GC-дескрипторов

#### 1. Маркировка корней

- Все объекты с флагами:
    
    - `Normal`
        
    - `Pinned`
        
- считаются **корнями**
    
- маркируются вместе со всеми зависимыми объектами
    

---

#### 2. Обработка Weak

- Если `Weak` указывает на **немаркированный объект**:
    
    - `Target` приравнивается к `null`
        

---

#### 3. Работа со списком финализации

- Немаркированные объекты:
    
    - перемещаются в **очередь на финализацию**
        
    - **маркируются** (становятся достижимыми)
        

---

#### 4. Обработка WeakTrackResurrection

- Если ссылка указывает на объект:
    
    - уже прошедший финализацию
        
- `Target` приравнивается к `null`
    

---

#### 5. Сжатие памяти

- GC:
    
    - устраняет фрагментацию
        
- Исключение:
    
    - объекты с флагом `Pinned` **не перемещаются**
        
    - соседние объекты — могут
        

---

### Использование Normal и Pinned с неуправляемым кодом

#### Normal — передача ссылки

Сценарий:

- неуправляемый код:
    
    - хранит ссылку
        
    - позже вызывает управляемый код
        

Алгоритм:

1. `GCHandle.Alloc(obj, Normal)`
    
2. Преобразование в `IntPtr`
    
3. Передача в native-код
    
4. Обратный вызов → `GCHandle.FromIntPtr`
    
5. Чтение `Target`
    
6. `Free()` после завершения работы
    

---

#### Pinned — передача адреса памяти

Сценарий:

- native-коду нужен **реальный адрес**
    
- объект **не должен перемещаться**
    

Пример:

- передача `String` в Win32
    
- асинхронный ввод-вывод (буферы)
    

Алгоритм:

1. `GCHandle.Alloc(obj, Pinned)`
    
2. `AddrOfPinnedObject()`
    
3. Передача адреса в native-код
    
4. После завершения — `Free()`
    

---

### P/Invoke и Pinned

📌 При использовании **P/Invoke**:

- CLR **автоматически**:
    
    - устанавливает `Pinned`
        
    - снимает его при возврате
        
- Явный `GCHandle` нужен:
    
    - если объект требуется native-коду **после возврата управления**
        

---

### Инструкция `fixed` в C#

#### Назначение

- Временная фиксация объекта
    
- Более эффективна, чем `GCHandle(Pinned)`
    

#### Как работает

- Компилятор:
    
    - устанавливает блокирующий флаг
        
    - запрещает перемещение объекта
        
- В конце блока:
    
    - ссылка обнуляется
        
    - объект снова доступен GC
        

📌 `fixed`:

- проще
    
- быстрее
    
- предпочтительнее для кратковременной фиксации
    

---

### Weak и WeakTrackResurrection в управляемом коде

#### Типичный сценарий Weak

- объект A **хочет пользоваться объектом B**
    
- но **не продлевать его жизнь**
    

Решение:

- A хранит `GCHandle(Weak)` вместо ссылки на B
    
- При вызове:
    
    - `Target != null` → B существует
        
    - `Target == null` → B уничтожен
        

---

### `WeakReference<T>`

#### Назначение

- Упрощённая и безопасная обёртка над `GCHandle`
    
- Поддерживает **только слабые ссылки**
    

#### Особенности

- Не требует специальных разрешений
    
- Работает только с `Weak` / `WeakTrackResurrection`
    
- ❌ Не поддерживает `Normal` и `Pinned`
    
- ❌ Требует размещения в куче
    
- ➜ тяжелее, чем `GCHandle`
    

---

###  ВАЖНО: слабые ссылки и кэширование ⚠️

❌ Ошибка мышления:

> «Слабые ссылки идеально подходят для кэша»

####  Почему это плохо

- GC запускается:
    
    - при заполнении поколения 0
        
    - а не при нехватке памяти
        
- В результате:
    
    - объекты уничтожаются **слишком рано**
        
    - производительность падает
        

#### Идеальный (но сложный) кэш

- Сначала:
    
    - строгие ссылки
        
- При нехватке памяти:
    
    - замена на слабые
        

📌 CLR **не уведомляет** о нехватке памяти  
(иногда используют `GlobalMemoryStatusEx`, `dwMemoryLoad > 80`)

---

### `ConditionalWeakTable<TKey, TValue>`

#### Назначение

- Связать **данные с объектом**
    
- Не продлевая время жизни объекта
    

#### Ключевая особенность

> Значение **гарантированно живо**,  
> пока жив ключ

Это **мощнее**, чем обычный `WeakReference`

---

### Поведение ConditionalWeakTable

- Ключ:
    
    - хранится как `WeakReference`
        
- Значение:
    
    - уничтожается **вместе с ключом**
        
- Потокобезопасен
    
- Повторный `Add` с тем же ключом:
    
    - `ArgumentException`
        

---

### Где применяется

- свойства зависимостей (XAML)
    
- динамические языки
    
- связывание метаданных с объектами
    
- отслеживание жизненного цикла объектов
    

---

### Итоговые выводы (экзаменационный минимум)

- `GCHandle`:
    
    - низкоуровневый механизм контроля жизни объектов
        
- `Normal` / `Pinned`:
    
    - управление временем жизни
        
- `Weak`:
    
    - мониторинг без продления жизни
        
- `WeakReference<T>`:
    
    - безопасная высокоуровневая обёртка
        
- `ConditionalWeakTable`:
    
    - ассоциативные данные без утечек памяти
        
- `Pinned`:
    
    - мощно, но опасно для производительности GC



# 🧨 3 Хостинг CLR и домены приложений
## 🔹 Хостинг CLR

### Общая идея
**Хостинг CLR** — механизм, позволяющий любому Windows-приложению запускать и управлять средой выполнения .NET (CLR) внутри своего процесса.

CLR работает поверх Windows, поэтому:
- управляемые сборки имеют формат **PE (EXE или DLL)**
- сама CLR реализована как **COM-сервер**

---

### Как загружается CLR

#### 1. CLR как COM-сервер
- CLR реализована в виде DLL
- Регистрируется в Windows через **GUID**
- Предоставляет стандартные COM-интерфейсы

---

#### 2. Запуск CLR хостом
Хост-приложение:

1. Вызывает `CLRCreateInstance`  
   (через библиотеку **MSCorEE.dll** — shim)

2. Получает интерфейс `ICLRMetaHost`

3. Через `GetRuntime` выбирает версию CLR

4. Получает:
   - `ICLRRuntimeInfo`
   - затем `ICLRRuntimeHost`

5. Управляет CLR через `ICLRRuntimeHost`

---

### Роль MSCorEE.dll (shim)

Это оболочка совместимости, которая:
- определяет, какую версию CLR загрузить
- поддерживает работу нескольких версий CLR
- существует в системе в одном экземпляре
- соответствует **последней установленной версии CLR**

---

### Где находится код CLR
Разные версии CLR лежат в отдельных папках и DLL:

- CLR 1.0–2.0 → `MSCorWks.dll`
- CLR 4.0 → `Clr.dll`

Можно устанавливать **несколько версий CLR** на одном компьютере.

---

### Выбор версии CLR

По умолчанию:
- версия берётся из управляемого EXE

Можно переопределить через конфигурационный файл:
- `requiredRuntime`
- `supportedRuntime`

---

### Что может делать хост через CLR

#### Управление средой выполнения
- запуск и инициализация CLR
- остановка выполнения управляемого кода
- загрузка и выполнение сборок

---

#### Управление ресурсами и поведением CLR
Хост может:

- участвовать в:
  - распределении памяти
  - планировании потоков
  - синхронизации
  - загрузке сборок

- получать уведомления:
  - начало/конец GC
  - выгрузка домена
  - исключения
  - остановка CLR

---

#### Ограничение возможностей CLR
Хост может:
- запрещать использование некоторых типов
- управлять отладкой
- перехватывать события выполнения

---

### Зачем нужен хостинг CLR

Позволяет приложениям:

- использовать управляемые языки
- получать JIT-компиляцию
- использовать сборку мусора
- выполнять код в изолированной среде
- применять готовую инфраструктуру разработки

---

### Важные ограничения

#### Выгрузка CLR
CLR нельзя выгрузить из процесса.
Единственный способ — завершить процесс.

---

#### Несколько версий CLR в процессе
- До .NET 4.0 — можно загрузить только одну версию CLR
- Начиная с .NET 4.0 — можно одновременно запускать:
  - CLR 2.0
  - CLR 4.0

---

### Полезный инструмент
`ClrVer.exe` — показывает версии CLR, загруженные в процесс.



## 🔹 Домены приложений (AppDomain)

### Общая идея
**Домен приложений** — логический контейнер внутри процесса, содержащий набор сборок.  
Создаётся CLR при запуске и обеспечивает **изоляцию кода и данных**.

- Первый домен — **основной (Default AppDomain)**
- Уничтожается только при завершении процесса
- Хост может создавать дополнительные домены

---

### Зачем нужны домены приложений

#### Изоляция
- Объекты принадлежат домену, в котором созданы
- Другие домены могут работать с ними только через:
  - marshal-by-reference
  - marshal-by-value
- Позволяет безопасно выгружать домены

---

#### Выгрузка
- CLR не умеет выгружать отдельные сборки
- Но может выгружать **целый домен вместе со всеми сборками**

---

#### Безопасность
- Для домена можно задать набор разрешений
- Позволяет запускать недоверенный код безопасно

---

#### Конфигурация
Каждый домен может иметь свои настройки:
- правила загрузки сборок
- пути поиска
- перенаправление версий
- теневое копирование
- параметры загрузчика

---

### Домены vs процессы

Windows-процессы:
- обеспечивают сильную изоляцию
- но дорогие по ресурсам

Домены приложений:
- обеспечивают изоляцию внутри одного процесса
- создаются значительно дешевле

---

### Особенности загрузки сборок и типов

- Каждый домен имеет:
  - собственную кучу загрузчика
  - собственные статические поля типов
  - собственный JIT-компилированный код

Даже если одна сборка загружена в несколько доменов:
- данные и код **не разделяются**

---

### Сборки, нейтральные к доменам

Некоторые сборки:
- загружаются один раз
- используются всеми доменами

Пример:
- `MSCorLib.dll`

⚠️ Такие сборки нельзя выгрузить без завершения процесса.

---

### Главные выводы
- AppDomain = лёгкая изоляция внутри процесса
- Позволяет безопасно выполнять и выгружать код
- Используется вместо создания отдельных процессов
- Некоторые системные сборки разделяются между доменами ради экономии ресурсов

## 🔹 Доступ к объектам из других доменов 

### Общая идея

Код одного **AppDomain** может работать с объектами другого домена, но только через специальные механизмы. Это нужно для сохранения изоляции доменов.

---

### Способы междоменного взаимодействия

#### 1. Продвижение по ссылке (Marshal-by-Reference)

- Тип должен наследоваться от `MarshalByRefObject`
    
- Вместо реального объекта передается **прокси (представитель)**
    
- Вызовы методов:
    
    - поток временно переключается в домен владельца объекта
        
    - метод выполняется там
        
- После выгрузки домена вызовы через прокси вызывают исключение
    

Особенности:

- Объект остаётся в исходном домене
    
- Есть потери производительности
    
- Доступ к полям особенно медленный
    
- Статические члены работают только в вызывающем домене
    

---

#### 2. Продвижение по значению (Marshal-by-Value)

- Тип должен иметь атрибут `[Serializable]`
    
- Объект:
    
    - сериализуется
        
    - копируется
        
    - десериализуется в другом домене
        

Особенности:

- Создается независимая копия объекта
    
- Выгрузка исходного домена не влияет на копию
    
- Состояния объектов в доменах не синхронизируются
    

---

#### 3. Отсутствие продвижения

Если тип:

- не наследует `MarshalByRefObject`
    
- не сериализуем
    

➡️ Объект нельзя передать между доменами  
➡️ Возникает `SerializationException`

---

### Работа потоков

- Поток может переходить между доменами
    
- В один момент времени поток выполняется только в одном домене
    
- Междоменный вызов всегда синхронный
    

---

### Время жизни удалённых объектов

CLR использует механизм **аренды (lease)**:

- Объект хранится ограниченное время
    
- Если вызовов нет — объект уничтожается сборщиком мусора
    
- Срок аренды можно переопределять
    

---

### Производительность

Междоменное взаимодействие:

- значительно медленнее обычных вызовов
    
- особенно медленный доступ к полям объектов MarshalByRef
    

---

### Оптимизации CLR

- Некоторые типы (например `String`) передаются без копирования
    
- Это возможно благодаря неизменяемости объектов
    

---

### Главные выводы

- Домены изолированы → прямые ссылки между ними запрещены
    
- Есть два основных способа обмена объектами:
    
    - через прокси (по ссылке)
        
    - через копирование (по значению)
        
- Не все типы можно передавать между доменами
    
- Междоменное взаимодействие дороже по производительности


## 🔹 Выгрузка доменов приложений

**AppDomain можно выгружать вместе со всеми сборками и ресурсами.**  
Для этого используется:

`AppDomain.Unload(domain)`

#### Что делает CLR при выгрузке домена:

1. **Приостанавливает все потоки**, которые выполняли управляемый код.
    
2. **Останавливает потоки, работающие с выгружаемым доменом**
    
    - Потокам принудительно генерируется `ThreadAbortException`
        
    - Потоки корректно завершаются через `finally`
        
    - При необработанном исключении:
        
        - поток завершается
            
        - процесс продолжает работать
            

⚠️ Потоки **не прерываются сразу**, если выполняют:

- `finally` или `catch`
    
- конструкторы типов
    
- критические секции
    
- неуправляемый код
    

3. **Помечает прокси-объекты**
    
    - Они узнают, что реальный объект уничтожен
        
    - Любой вызов → `AppDomainUnloadedException`
        
4. **Запускается сборщик мусора**
    
    - Освобождается память домена
        
    - Вызываются финализаторы объектов
        
5. **Возобновляется выполнение потоков**
    

---

#### Дополнительные особенности

- Выгрузка выполняется **синхронно**
    
- CLR ждёт до **10 секунд**, пока потоки покинут домен
    
- Если не удалось выгрузить → `CannotUnloadAppDomainException`
    
- Если выгрузку вызывает поток из самого домена:
    
    - CLR создаёт вспомогательный поток для выгрузки
        

---

## 🔹 Мониторинг доменов приложений

CLR позволяет отслеживать использование ресурсов доменом.

Мониторинг включается вручную:

`AppDomain.MonitoringEnabled = true;`

⚠️ После включения отключить нельзя.

---

#### Основные показатели мониторинга

##### Память процесса

- `MonitoringSurvivedProcessMemorySize`
    
    - Память, используемая всеми доменами
        

##### Память домена

- `MonitoringTotalAllocatedMemorySize`
    
    - Всего выделено памяти доменом
        
- `MonitoringSurvivedMemorySize`
    
    - Память, пережившая сборку мусора
        

##### Время процессора

- `MonitoringTotalProcessorTime`
    
    - CPU-время домена
        

---

#### Назначение мониторинга

- Контроль потребления ресурсов
    
- Автоматическая выгрузка перегруженных доменов
    
- Анализ производительности алгоритмов
    

---

## 🔹 Уведомления о первом исключении (FirstChanceException)

Каждый домен может отслеживать **все создаваемые исключения**.

Используется событие:

`AppDomain.FirstChanceException`

---

#### Как работает механизм

1. При возникновении исключения CLR:
    
    - вызывает обработчики `FirstChanceException`
        
    - затем ищет `catch`
        
2. Если исключение не обработано:
    
    - передаётся выше по стеку
        
    - сериализуется между доменами
        
    - снова вызывает `FirstChanceException`
        
3. Если исключение никто не обработал:
    
    - CLR завершает процесс
        

---

#### Важно

Обработчики FirstChanceException:

- НЕ могут обработать исключение
    
- Используются только для:
    
    - логирования
        
    - мониторинга ошибок
        
    - диагностики
        

---

### 📌 Главные тезисы главы

- Домены можно безопасно выгружать вместе со всеми ресурсами
    
- CLR аккуратно завершает потоки через исключения
    
- Есть встроенный мониторинг ресурсов доменов
    
- Можно отслеживать все возникающие исключения через события
    
- Изоляция доменов строго поддерживается CLR


## 🔹Использование хостами доменов приложений

---

###  Общая идея

Хост — это приложение, которое:

- загружает CLR
    
- управляет доменами приложений
    
- контролирует выполнение управляемого кода
    

Разные типы приложений используют домены по-разному.

---

### 🔸 Саморазмещаемые исполняемые приложения

(консольные, службы Windows, WinForms, WPF)

#### Как запускаются

1. Windows запускает EXE.
    
2. Загружается **оболочка совместимости CLR**.
    
3. Она:
    
    - читает заголовок сборки
        
    - определяет нужную версию CLR
        
    - загружает её
        
4. CLR находит метод `Main` и запускает приложение.
    

---

#### Работа со сборками

- При обращении к типу из другой сборки:
    
    - CLR загружает её в тот же домен
        
- После завершения `Main`:
    
    - завершается процесс
        
    - уничтожаются все домены
        

---

#### Корректное завершение процесса

Используется:

`Environment.Exit()`

Он:

- вызывает финализаторы объектов
    
- освобождает COM-ресурсы
    
- завершает процесс через Win32
    

---

### Дополнительно

Приложение может самостоятельно создавать новые домены внутри процесса.

---

### 🔸 Silverlight

(браузерные интернет-приложения)

#### Особенности работы

- Использует собственную версию CLR
    
- Каждый элемент Silverlight:
    
    - запускается в отдельном домене
        
- При закрытии вкладки:
    
    - домены выгружаются
        

---

#### Безопасность

Код выполняется в **sandbox**:

- ограниченные права
    
- защита системы и пользователя
    

---

### 🔸 ASP.NET и веб-службы

ASP.NET выступает как хост CLR.

#### Первый запрос к веб-приложению

1. ASP.NET загружает CLR
    
2. Создаётся новый домен приложения
    
3. Загружаются сборки сайта
    
4. Создаётся объект обработчика
    
5. Выполняется запрос клиента
    

---

#### Повторные запросы

- Новый домен не создаётся
    
- Создаётся только новый экземпляр обработчика
    
- Код уже JIT-скомпилирован → быстрее выполнение
    

---

#### Несколько веб-приложений

- Каждое приложение:
    
    - имеет собственный домен
        
    - изолировано от других
        
- Несколько доменов могут работать в одном процессе → выше производительность
    

---

#### Горячее обновление сайта

ASP.NET умеет:

- отслеживать изменения файлов
    
- выгружать старый домен
    
- создавать новый домен с обновлённым кодом
    

Используется механизм:  
👉 теневое копирование (shadow copying)

---

### 🔸 Microsoft SQL Server

SQL Server — неуправляемое приложение (C++), но поддерживает CLR.

#### Как работает

- При первом вызове управляемой хранимой процедуры:
    
    - SQL Server загружает CLR
        
- Процедуры выполняются:
    
    - в отдельном защищённом домене
        

---

#### Преимущества управляемых процедур

- Можно писать на языках .NET
    
- Используется строгая типизация
    
- JIT-компиляция → высокая производительность
    
- Можно использовать библиотеки FCL
    
- Упрощается разработка
    

---

### 📌 Главные выводы главы

- Домены приложений позволяют:
    
    - изолировать код
        
    - безопасно выгружать приложения
        
    - повышать производительность
        
- Разные хосты используют домены по-разному:
    
    - EXE — обычно один основной домен
        
    - Silverlight — домен на элемент управления
        
    - ASP.NET — домен на веб-приложение
        
    - SQL Server — домен для управляемых процедур


## 🔹 Нетривиальное управление хостингом CLR — конспект

---

###  Общая идея

CLR предоставляет хостам расширенные механизмы контроля над:

- созданием доменов приложений
    
- безопасностью
    
- обработкой сбоев
    
- управлением потоками
    
- выполнением стороннего кода
    

---

### 🔸 Использование AppDomainManager

#### Назначение

Позволяет хосту **изменять стандартное поведение CLR** через управляемый код.

---

#### Как используется

1. Создаётся класс-наследник:
    

`System.AppDomainManager`

2. Класс:
    

- компилируется в сборку
    
- размещается в GAC
    
- получает полное доверие
    

3. CLR заставляют использовать его через:
    

- `AppDomainSetup`
    
- конфигурационный файл
    
- интерфейс `ICLRControl`
    

---

#### Возможности AppDomainManager

Позволяет хосту:

✔ изменять параметры безопасности  
✔ изменять конфигурацию доменов  
✔ запрещать создание новых доменов  
✔ возвращать уже существующие домены  
✔ управлять контекстом выполнения  
✔ управлять разрешениями сборок

CLR автоматически создаёт экземпляр этого менеджера в каждом новом домене.

---

### 🔸 Надёжность хост-приложений

Хост может задавать реакцию CLR на сбои управляемого кода.

#### Возможные уровни реакции (от мягкого к жёсткому)

1. Прерывание потока
    
2. Выгрузка домена
    
3. Отключение CLR
    
4. Завершение всего процесса
    

---

#### Корректное vs принудительное завершение

##### Корректное завершение

- выполняются блоки `finally`
    
- вызываются финализаторы
    
- поток завершается безопасно
    

##### Принудительное завершение

- код очистки игнорируется
    
- используется при серьёзных сбоях
    

---

#### Ограничения завершения потоков

Нельзя завершить поток, если он:

- выполняет неуправляемый код
    
- находится в критической области (CER)
    

---

### 🔸 Политика расширения (Escalation Policy)

Определяет, что делать при сбоях.

Пример:

- CLR сначала пытается корректно завершить поток
    
- если не получилось → принудительное завершение
    
- если поток в критической области:
    
    - CLR пытается выгрузить весь домен
        

Причина: поток может повреждать общие данные.

---

### 🔸 Возвращение управления потоком хосту

#### Проблема

Хост часто запускает сторонний код.  
Этот код может:

- зависнуть
    
- уйти в бесконечный цикл
    
- блокировать поток
    

---

#### Решение — архитектура контроля

Последовательность работы

1. Клиент отправляет запрос
    
2. Сервер передаёт задачу потоку из пула
    
3. Поток выполняет доверенный код
    
4. Доверенный код вызывает сторонний код в отдельном домене
    
5. Если сторонний код зависает:
    
    - хост вызывает `Thread.Abort()`
        
6. Поток получает `ThreadAbortException`
    
7. Поток выполняет `finally`
    
8. Хост перехватывает исключение и возвращает поток в пул
    

---

#### Как работает Thread.Abort

- Выполняется асинхронно
    
- Помечает поток флагом `AbortRequested`
    
- CLR ждёт, пока поток достигнет безопасной точки (safe place)
    

---

*Безопасные точки*

Поток можно остановить если он:

- простаивает
    
- заблокирован управляемой синхронизацией
    

Поток нельзя остановить если он выполняет:

- `catch`
    
- `finally`
    
- конструктор типа
    
- критическую область
    
- неуправляемый код
    

---

####  Особенности ThreadAbortException

- Даже если исключение перехвачено:
    
    - CLR автоматически генерирует его повторно
        

---

#### Как хост сохраняет контроль

Используется:

`Thread.ResetAbort()`

Он запрещает повторную генерацию исключения.

---

#### Безопасность

Сторонний код не может вызвать `ResetAbort`, если:

- у него нет разрешения `SecurityPermission(ControlThread)`
    

Хост специально не выдаёт это разрешение.

---

### 🔸 Потенциальные проблемы

Сторонний код может:

- зависнуть внутри `catch` или `finally`
    
- выбросить другое исключение
    

---

#### Решение

CLR может усилить меры:

- принудительно остановить поток
    
- выгрузить домен
    
- отключить CLR
    
- завершить процесс
    

---

### 🔸 Передача данных при Abort

Метод:

`Thread.Abort(object state)`

Позволяет передать информацию в исключение:

`ThreadAbortException.ExceptionState`

Используется хостом для передачи причины остановки потока.

---

### 📌 Главные выводы главы

- Хост может полностью контролировать выполнение CLR
    
- AppDomainManager позволяет менять поведение доменов
    
- CLR поддерживает гибкие стратегии обработки сбоев
    
- Thread.Abort — ключевой инструмент возврата контроля
    
- Для безопасности сторонний код выполняется:
    
    - в отдельных доменах
        
    - с ограниченными разрешениями
        
- При серьёзных сбоях CLR может завершить домен, поток или процесс

# 🧨 4 Загрузка сборок и отражение


## 🔸 О чём глава

Глава посвящена:

- загрузке сборок во время выполнения
    
- получению информации о типах
    
- созданию экземпляров неизвестных на этапе компиляции типов
    
- построению динамически расширяемых приложений (add-ins)
    

---

### 🔸 Динамически расширяемые приложения

#### Идея

- Одна компания создаёт **хост**
    
- Другие создают **подключаемые компоненты (add-ins)**
    
- Хост не знает о них во время компиляции
    
- Он находит и загружает их во время выполнения
    

---

#### Связь с доменами приложений

Хост может:

- загружать add-in в отдельный AppDomain
    
- задавать для него ограничения безопасности
    
- выгружать add-in через выгрузку домена
    


---

## 🔹 Загрузка сборок

Когда JIT компилирует метод:

1. Он анализирует ссылки на типы
    
2. По таблицам `TypeRef` и `AssemblyRef` определяет:
    
    - имя сборки
        
    - версию
        
    - культуру
        
    - открытый ключ
        
3. CLR пытается загрузить сборку в домен
    

---

### 🔸 Assembly.Load

Основной способ загрузки:

`Assembly.Load(AssemblyName) Assembly.Load(string)`

#### Что делает Load:

- применяет политику перенаправления версий
    
- ищет сборку:
    
    - в GAC
        
    - в базовом каталоге
        
    - в private path
        
    - в codeBase
        
- возвращает объект `Assembly`
    

Если не найдено → `FileNotFoundException`

---

#### Особенности

- Для строгого имени учитываются:
    
    - версия
        
    - культура
        
    - ключ
        
- Для нестрогого имени:
    
    - политика не применяется
        
    - GAC не используется
        

---

### 🔸 Assembly.LoadFrom

Используется, когда известен путь к файлу:

`Assembly.LoadFrom(string path)`

### Алгоритм:

1. Извлекает AssemblyName из файла
    
2. Вызывает `Assembly.Load`
    
3. Если не найдено через политику:
    
    - загружает сборку напрямую по указанному пути
        

---

#### Можно загружать по URL

`Assembly.LoadFrom("http://...")`

CLR:

- скачивает файл
    
- помещает в кэш
    
- загружает оттуда
    

---

#### Опасность LoadFrom

Если в системе есть другая сборка с тем же строгим именем:

- может загрузиться не тот файл
    
- поведение станет непредсказуемым
    

Рекомендация:

- всегда менять версию при сборке
    

---

### 🔸 Assembly.LoadFile

- Загружает сборку строго по пути
    
- Не применяет политику
    
- Не разрешает зависимости автоматически
    
- Часто используется инструментами (например дизайнеры VS)
    

Зависимости нужно обрабатывать вручную через событие `AssemblyResolve`.

---

### 🔸 ReflectionOnlyLoad / ReflectionOnlyLoadFrom

Используются, когда:

- нужно только анализировать метаданные
    
- код выполнять не нужно
    

`Assembly.ReflectionOnlyLoadFrom(...) Assembly.ReflectionOnlyLoad(...)`

---

#### Особенности:

- Код сборки нельзя выполнить
    
- Попытка выполнения → `InvalidOperationException`
    
- Можно загружать:
    
    - сборки другой архитектуры
        
    - сборки с отложенной подписью
        
    - сборки с особыми разрешениями
        

---

#### Важный момент

CLR НЕ разрешает зависимости автоматически.

Нужно подписываться на событие:

`AppDomain.ReflectionOnlyAssemblyResolve`

И вручную загружать зависимости.

---

### 🔹 Выгрузка сборок

❗ CLR не позволяет выгружать отдельные сборки.

Причина:

- поток может вернуться в выгруженную сборку
    
- это приведёт к сбою
    

Решение:

- можно выгрузить только весь AppDomain
    

---

Даже сборки, загруженные через ReflectionOnly, нельзя выгрузить отдельно.

---

### 🔹 Встраивание зависимых DLL в EXE

Иногда распространяют один EXE вместо набора DLL.

#### Как это делается:

1. DLL добавляются в проект
    
2. Build Action → `Embedded Resource`
    
3. DLL встраиваются в EXE
    

---

#### Проблема

CLR не найдёт зависимые сборки автоматически.

---

#### Решение — событие AssemblyResolve

При запуске регистрируется обработчик:

`AppDomain.CurrentDomain.AssemblyResolve += ResolveHandler;`

Обработчик:

- ищет DLL среди ресурсов
    
- читает поток
    
- загружает через `Assembly.Load(byte[])`
    

---

#### Минус подхода

- увеличивается потребление памяти
    
- DLL загружается в память полностью


## 🔹  Использование отражения для создания динамически расширяемых приложений — конспект

---

### 🔹 1. Что такое отражение

Метаданные сборки — это таблицы:

- типы
    
- поля
    
- методы
    
- свойства
    
- события
    
- атрибуты
    

Пространство имён **System.Reflection** предоставляет объектную модель для работы с этими таблицами.

С помощью отражения можно:

- перечислить все типы сборки
    
- узнать их базовые типы
    
- получить интерфейсы
    
- прочитать атрибуты
    
- получить IL-код метода
    
- построить инструмент наподобие ILDasm
    

---

### 🔹 2. Где реально используется отражение

Обычно не в прикладном коде, а внутри библиотек:

- сериализация (определяет поля типа)
    
- дизайнеры Visual Studio (определяют свойства)
    
- ORM и DI-контейнеры
    
- плагинные системы
    
- позднее связывание
    

---

### 🔹 3. Позднее и раннее связывание

### Раннее связывание (early binding)

Тип известен на этапе компиляции.

### Позднее связывание (late binding)

Тип определяется во время выполнения:

- загрузка сборки
    
- поиск типа по имени
    
- создание экземпляра
    
- вызов метода через отражение
    

Аналогия с Win32:

- `LoadLibrary`
    
- `GetProcAddress`
    

---

### 🔹 4. Недостатки отражения

#### ❌ 1. Потеря безопасности типов

Работа через строки:

Type.GetType("int") // вернёт null

CLR знает тип как:

System.Int32

Ошибки проявляются только во время выполнения.

---

#### ❌ 2. Низкая производительность

Причины:

- поиск по строкам
    
- упаковка параметров в object[]
    
- проверка типов аргументов
    
- проверка безопасности
    
- извлечение аргументов в стек
    

Вызов метода через отражение значительно медленнее обычного.

---

### 🔹 5. Как правильно использовать отражение

Лучше:

#### ✅ Подход 1 — Базовый класс

- создать базовый тип
    
- загружать тип через отражение
    
- приводить к базовому типу
    
- вызывать виртуальные методы
    

#### ✅ Подход 2 — Интерфейс (предпочтительный)

- определить интерфейс
    
- загруженный тип реализует его
    
- привести к интерфейсу
    
- вызывать методы напрямую
    

Плюсы интерфейса:

- гибкость
    
- меньше ограничений
    

Минус:

- нельзя добавлять методы без перекомпиляции реализаций
    

⚠ Рекомендуется:

- базовый тип/интерфейс помещать в отдельную сборку (для версионирования)
    

---

### 🔹 6. Поиск типов в сборке

Пример типичного сценария:

Assembly a = Assembly.Load(...);  
  
foreach (Type t in a.ExportedTypes)  
{  
    Console.WriteLine(t.FullName);  
}

`ExportedTypes` возвращает только публичные типы.

---

### 🔹 7. Объект Type

`System.Type` — ссылка на тип.

Способы получения:

#### 1️⃣ Через объект

o.GetType()

#### 2️⃣ Через typeof (быстрее)

typeof(FileInfo)

#### 3️⃣ Через Type.GetType(string)

Type.GetType("System.Int32")

Можно указывать сборку:

"System.Int32, mscorlib, Version=..., PublicKeyToken=..."

---

#### Важно

`typeof()` — раннее связывание  
`GetType()` — позднее связывание

---

### 🔹 8. Точное и совместимое сравнение типов

if (o.GetType() == typeof(FileInfo))

Это **точное совпадение**, без учёта наследников.

Для совместимости:

- оператор `is`
    
- оператор `as`
    
- `IsAssignableFrom`
    

---

### 🔹 9. Type vs TypeInfo

- `Type` — ссылка на тип
    
- `TypeInfo` — определение типа (больше информации)
    

Получение:

TypeInfo info = type.GetTypeInfo();

Через TypeInfo можно узнать:

- IsPublic
    
- IsAbstract
    
- IsSealed
    
- IsClass
    
- IsValueType
    
- BaseType
    
- Assembly
    
- Module
    
- FullName
    

Получение TypeInfo может потребовать загрузки сборки → операция дорогая.

---

### 🔹 10. Пример: построение дерева исключений

Алгоритм:

1. Загрузить нужные сборки
    
2. Получить все типы:
    
    AppDomain.CurrentDomain.GetAssemblies()
    
3. Отфильтровать типы:
    

`typeof(Exception)  
    .GetTypeInfo()  
    .IsAssignableFrom(t.GetTypeInfo())`

4. Отсортировать
    
5. Рекурсивно построить дерево наследования
    

---

### Что показывает пример

- массовое использование отражения
    
- анализ типов во всех загруженных сборках
    
- построение иерархии по BaseType
    
- проверка наследования через IsAssignableFrom
    

---

### 🔹 11. ReflectionOnly сценарии

Если сборки загружены через:

- `ReflectionOnlyLoad`
    
- `ReflectionOnlyLoadFrom`
    

Можно:

- анализировать метаданные
    

Нельзя:

- выполнять код
    

---

### 🔹 Главное из раздела

Отражение позволяет:

- загружать неизвестные типы
    
- анализировать их структуру
    
- создавать экземпляры
    
- вызывать методы
    
- строить плагины
    

Но:

- оно медленное
    
- небезопасное на этапе компиляции
    
- должно использоваться ограниченно
    

Лучший паттерн:

> Использовать отражение только для создания экземпляра,  
> а дальше работать через интерфейс или базовый тип.



## 🔹  Создание экземпляра типа

### 1️⃣ `System.Activator.CreateInstance`

Самый распространённый способ.

#### Варианты:

- Принимает `Type`  
    → возвращает ссылку на созданный объект  
    → можно передать аргументы конструктора
    
- Принимает строки (имя типа + имя сборки)  
    → возвращает `ObjectHandle`  
    → позволяет создавать удалённые объекты
    

---

#### 🔸 ObjectHandle

- используется для передачи объектов между доменами
    
- требует вызова `Unwrap()`
    
- поддерживает:
    
    - маршалинг по ссылке (создаётся proxy)
        
    - маршалинг по значению (десериализация копии)
        

---

### 2️⃣ `Activator.CreateInstanceFrom`

Отличие от `CreateInstance`:

- тип и сборка задаются строками
    
- сборка загружается через `Assembly.LoadFrom`
    
- всегда возвращается `ObjectHandle`
    
- требуется `Unwrap()`
    

---

### 3️⃣ Методы `AppDomain`

Позволяют создать объект в конкретном домене приложений:

- `CreateInstance`
    
- `CreateInstanceAndUnwrap`
    
- `CreateInstanceFrom`
    
- `CreateInstanceFromAndUnwrap`
    

Методы с `AndUnwrap` удобнее — не требуют дополнительного вызова `Unwrap()`.

---

### 4️⃣ Через `ConstructorInfo.Invoke`

Алгоритм:

1. Получить `Type`
    
2. Найти нужный конструктор
    
3. Вызвать `ConstructorInfo.Invoke`
    

Объект создаётся в текущем домене.

---

### 🔹 Особенности

#### ⚠ Значимые типы (struct)

- CLR не требует наличия конструктора
    
- Обычные механизмы вызывают конструктор
    
- Но `Activator.CreateInstance(Type)`  
    может создать struct без вызова конструктора
    

---

##3 🔹 Ограничения

Через описанные механизмы нельзя создать:

- массивы (`System.Array`)
    
- делегаты (`System.MulticastDelegate`)
    

---

### Создание массива

Используется:

Array.CreateInstance(Type elementType, ...)

Позволяет задать:

- размерность
    
- границы
    

---

### Создание делегата

Используется:

Delegate.CreateDelegate(...)

Нужно указать:

- тип делегата
    
- метод (статический или экземплярный)
    

---

### 🔹 Создание экземпляра обобщённого типа

Алгоритм:

1. Получить открытый тип
    
    typeof(Dictionary<,>)
    
2. Закрыть его через `MakeGenericType`
    
    openType.MakeGenericType(...)
    
3. Создать экземпляр через `Activator.CreateInstance`
    

Результат:

Dictionary<string, int>

---

### 📌 Главное

Создание объектов через отражение возможно через:

- `Activator`
    
- `AppDomain`
    
- `ConstructorInfo`
    
- специальные методы для массивов и делегатов
    
- `MakeGenericType` для обобщённых типов
    

Используется в:

- плагинных системах
    
- DI-контейнерах
    
- сериализации
    
- инфраструктурных библиотеках

## 🔹 Создание приложений с поддержкой подключаемых компонентов
### 🔹 1. Основа архитектуры — интерфейс

Для расширяемых приложений:

- Центральный элемент — **интерфейс**
    
- Он определяет контракт между хостом и add-in
    
- Интерфейс предпочтительнее базового класса  
    (разработчик add-in может выбрать свою иерархию)
    

---

### 🔹 2. Правильная структура сборок

#### ✅ 1. Сборка SDK (контракт)

Содержит:

- интерфейс (например `IAddIn`)
    
- при необходимости — общие типы данных
    

Требования:

- дать строгое имя
    
- не изменять интерфейс после публикации
    
- изменения → новая версия + файл политики издателя
    

⚠ Лучше использовать типы из `mscorlib` (избегаются конфликты версий).

---

#### ✅ 2. Сборки подключаемых модулей

- Реализуют интерфейс SDK
    
- Ссылаются только на SDK
    
- Могут обновляться независимо
    

---

#### ✅ 3. Сборка хоста

- Ссылается на SDK
    
- Не зависит от конкретных add-in
    
- Может свободно обновляться
    

---

### 🔹 3. Версионирование — ключевой момент

- Типы для межсборочного взаимодействия → в отдельной сборке
    
- Интерфейсы менять нельзя
    
- Добавлять новые члены в классы можно
    
- При изменениях → новая версия + publisher policy
    

---

### 🔹 4. Механизм загрузки add-in

Типичный алгоритм хоста:

1. Найти DLL в каталоге
    
2. Загрузить сборки (`Assembly.Load`)
    
3. Получить экспортируемые типы
    
4. Отфильтровать:
    
    - класс
        
    - реализует интерфейс (`IsAssignableFrom`)
        
5. Создать экземпляр через `Activator.CreateInstance`
    
6. Привести к интерфейсу и использовать
    

---

### 🔹 5. Важный принцип

Отражение используется только для:

- поиска типа
    
- создания экземпляра
    

Дальше работа идёт через интерфейс → типобезопасно и быстро.

---

### 🔹 6. Домены приложений (реальный сценарий)

В продакшене add-in:

- создаются в отдельных AppDomain
    
- получают собственные настройки безопасности
    
- могут быть выгружены
    

Для междоменного взаимодействия:

- типы должны наследоваться от `MarshalByRefObject`
    
- создаются proxy-объекты
    

Хост управляет загрузкой и выгрузкой модулей через домены.

---

### 🔹 7. Готовые решения

Microsoft предлагает **MEF (Managed Extensibility Framework)** — библиотеку, упрощающую:

- регистрацию
    
- поиск
    
- загрузку компонентов

### 📌 Главное

Архитектура расширяемого приложения:

[Host] → использует → [SDK (интерфейс)]  
                ↑  
        реализуют  
         [Add-ins]

Ключевые принципы:

- контракт в отдельной сборке
    
- стабильность интерфейса
    
- изоляция через домены
    
- отражение только на этапе инициализации

## 🔹 Нахождение членов типа путем отражения — краткий конспект

---

### 🔹 1. Зачем искать члены через отражение

Используется в:

- инструментах анализа (ILDasm, FxCop)
    
- дизайнерах форм
    
- механизмах сериализации
    
- библиотеках привязки данных
    

⚠ В обычных приложениях лучше избегать — теряется производительность и безопасность типов.

---

### 🔹 2. Члены типа

Членами типа являются:

- поля
    
- конструкторы
    
- методы
    
- свойства
    
- события
    
- вложенные типы
    

Базовый класс для всех — **MemberInfo** (`System.Reflection`).

---

### 🔹 3. Иерархия отражения

Навигация происходит так:

AppDomain  
  → Assembly  
    → Module  
      → Type  
        → MemberInfo (FieldInfo, MethodInfo и др.)

---

### 🔹 4. Основные свойства MemberInfo

Общие для всех членов:

- `Name` — имя
    
- `DeclaringType` — объявляющий тип
    
- `Module` — модуль
    
- `CustomAttributes` — атрибуты
    

---

### 🔹 5. Получение членов типа

Через `TypeInfo`:

- `DeclaredMembers` — все члены
    
- `GetDeclaredField`
    
- `GetDeclaredMethod`
    
- `GetDeclaredProperty`
    
- `GetDeclaredEvent`
    
- `GetDeclaredNestedType`
    
- `GetDeclaredMethods(string)`
    

Дополнительно:

- `GetParameters()` — параметры
    
- `ReturnParameter` — возвращаемое значение
    
- `GetGenericArguments()` — обобщения
    
- `GetCustomAttributes()` — атрибуты
    

---

### 🔹 6. Обращение к членам

|Тип|Как вызывать|
|---|---|
|**FieldInfo**|`GetValue` / `SetValue`|
|**ConstructorInfo**|`Invoke`|
|**MethodInfo**|`Invoke`|
|**PropertyInfo**|`GetValue` / `SetValue`|
|**EventInfo**|`AddEventHandler` / `RemoveEventHandler`|

---

### 🔹 7. Три способа вызова через отражение

#### 1️⃣ Прямая привязка + Invoke

- Получаем `MethodInfo`
    
- Вызываем `Invoke`
    
- Медленно, но универсально
    

---

#### 2️⃣ Привязка + создание делегата

- Через `CreateDelegate`
    
- Вызов почти как обычный метод
    
- Быстрее при многократных вызовах
    

⚠ Нельзя создать делегат для поля.

---

#### 3️⃣ Использование `dynamic`

- Синтаксис проще
    
- Связывание кэшируется
    
- Быстро при повторных вызовах
    
- Соблюдает уровни доступа (private нельзя вызвать)
    

---

### 🔹 8. Работа с ref-параметрами

В строковых именах типов:

System.Int32&

`&` — означает передачу по ссылке.

Альтернатива:

typeof(Int32).MakeByRefType()

---

### 🔹 9. Оптимизация памяти — Runtime*Handle

Объекты `Type`, `MethodInfo`, `FieldInfo` занимают много памяти.

CLR использует компактные дескрипторы:

- `RuntimeTypeHandle`
    
- `RuntimeFieldHandle`
    
- `RuntimeMethodHandle`
    

Это структуры с `IntPtr` → занимают мало памяти.

---

#### Преобразования

- `Type` ↔ `RuntimeTypeHandle`
    
- `FieldInfo.FieldHandle`
    
- `MethodInfo.MethodHandle`
    
- `GetMethodFromHandle`
    
- `GetTypeFromHandle`
    

---

### 🔹 10. Практический вывод

- Хранить `MethodInfo` дорого по памяти
    
- Лучше кэшировать `RuntimeMethodHandle`
    
- При необходимости восстанавливать `MethodInfo`
    

Эксперимент показывает:  
кэш `MethodInfo` потребляет **мегабайты**,  
кэш `RuntimeMethodHandle` — в разы меньше.

---

### 📌 Главное

Отражение позволяет:

- находить структуру типов
    
- анализировать метаданные
    
- вызывать члены динамически
    

Но:

- это медленно
    
- потребляет много памяти
    
- снижает безопасность типов
    

👉 Использовать только там, где это действительно необходимо (инструменты, фреймворки, инфраструктурный код).

# 🧨 5 Современная сериализация в .NET
P.S. это не по Рихтеру, тк он рассматривает устаревший вариант

## 🔹 1. Основной стандарт сегодня

### ✅ `System.Text.Json`

Пространство имён:  
`System.Text.Json`

Это:

- встроенная библиотека
    
- быстрая
    
- безопасная
    
- используется по умолчанию в ASP.NET Core
    

---

## 🔹 2. Базовое использование

```cs
using System.Text.Json;  
  
var json = JsonSerializer.Serialize(obj);  
var obj2 = JsonSerializer.Deserialize<MyType>(json);
```

Работает:

- без `[Serializable]`
    
- без наследования
    
- без специальных интерфейсов
    

---

## 🔹 3. Что сериализуется по умолчанию

### ✔ Публичные свойства (`public get/set`)

### ❌ Private-поля — не сериализуются

Пример:

```cs
public class Person  
{  
    public string Name { get; set; }  
    public int Age { get; set; }  
  
    private string Secret; // не попадёт в JSON  
}
```

---

## 🔹 4. Управление сериализацией

Через атрибуты:

- `[JsonIgnore]`
    
- `[JsonPropertyName("custom_name")]`
    
- `[JsonConstructor]`
    
- `[JsonInclude]` (для non-public)
    

Пример:

public class Person  
{  
    [JsonPropertyName("full_name")]  
    public string Name { get; set; }  
  
    [JsonIgnore]  
    public string Password { get; set; }  
}

---

## 🔹 5. Настройки сериализации

var options = new JsonSerializerOptions  
{  
    WriteIndented = true,  
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase  
};

Частые настройки:

- CamelCase
    
- IgnoreNullValues
    
- Converters
    
- Reference handling
    

---

## 🔹 6. Работа со ссылками (циклы)

По умолчанию циклы вызывают ошибку.

Можно включить:

ReferenceHandler = ReferenceHandler.Preserve

---

## 🔹 7. Кастомные конвертеры

Если нужно сериализовать тип особым образом:

```cs
public class MyConverter : JsonConverter<MyType>

Используется для:

- value objects
    
- DateOnly / TimeOnly
    
- специфичных форматов
    
```
---

## 🔹 8. Immutable-объекты

Поддерживаются:

- record
    
- init-only
    
- конструктор с параметрами
    

public record Person(string Name, int Age);

Работает из коробки.

---

## 🔹 9. Полиморфизм

В .NET 7+ есть поддержка через:

[JsonPolymorphic]  
[JsonDerivedType(typeof(Dog))]

Раньше было сложно — сейчас встроенная поддержка.

---

## 🔹 10. Производительность

`System.Text.Json`:

- быстрее Newtonsoft
    
- использует Span
    
- работает без рефлексии при source generation
    

---

## 🔹 11. Source Generation (очень важно)

Можно избежать рефлексии полностью:

```cs
[JsonSerializable(typeof(Person))]  
internal partial class MyJsonContext : JsonSerializerContext  
{  
}
```

Даёт:

- максимум производительности
    
- AOT-совместимость
    
- минимальный аллокации
    

Используется в production high-load сервисах.

---

## 🔹 12. Альтернативы

### 🔸 Newtonsoft.Json

Более гибкий, но:

- медленнее
    
- legacy-проект
    
- используется в старых системах
    

---

### 🔸 DataContractSerializer

Используется редко.  
Атрибуты:

- `[DataContract]`
    
- `[DataMember]`
    

Более строгая модель.

---

### 🔸 Протоколы для high-performance

- MessagePack
    
- protobuf
    
- MemoryPack
    

Используются для:

- микросервисов
    
- RPC
    
- high-load систем
    

---

## 🔹 13. Главное отличие от старой CLR-сериализации

|Старый подход|Современный подход|
|---|---|
|`[Serializable]`|не нужен|
|сериализация private-полей|только public-свойства|
|`BinaryFormatter`|запрещён|
|сохраняется имя сборки|сохраняется только JSON|
|небезопасно|безопасно|

---

## 🔹 14. Когда что использовать

### Веб API → `System.Text.Json`

### Высокая производительность → Source Gen / MessagePack

### Старый проект → Newtonsoft

### Внутренний RPC → protobuf / MessagePack

Современная сериализация в .NET:
